Overview

BASIC++ provides a software interrupt system inspired by the
DOS TSR (Terminate and Stay Resident) model. Instead of hooking
hardware interrupt vectors (INT 08h, INT 09h, INT 1Ch), BASIC++
uses cooperative event polling between statements. The result is
functionally identical to a TSR for BASIC programs: background
handlers fire automatically without explicit polling in the
main program.

This tutorial covers:
  1. Timer-based events (screensavers, clocks, auto-save)
  2. Keyboard interrupt handlers (hotkeys, function keys)
  3. Device I/O events (serial ports, USB, network)
  4. Mouse/pointer events
  5. Signal/break handlers
  6. Combining events for complex systems
  7. Building a text-based screensaver engine
  8. Integration with TUI desktops

------------------------------------------------------------
1. How Events Work (The Virtual ISR Model)
------------------------------------------------------------

1.1 The Event Polling Loop

Between every BASIC statement, the interpreter calls event_poll().
This function checks all registered event sources in priority
order, similar to how a hardware interrupt controller works:

  Priority   Event Class        DOS Equivalent
  --------   ---------------    ----------------------
  Highest    BREAK (Ctrl+C)     INT 23h (SIGINT)
  Level 1    TIMER              INT 1Ch (timer tick)
  Level 1.5  KEY                INT 09h (keyboard)
  Level 2    DEVICE (VDev)      Hardware IRQs
  Level 2.5  COM (serial)       INT 0Ch/0Bh (COM1/COM2)
  Level 2.5  PEN (pointer)      INT 33h (mouse driver)
  Level 2.5  MOUSE              INT 33h
  Level 2.5  STRIG (joystick)   INT 0Fh (game port)
  Level 2.5  PLAY (music)       Sound Blaster IRQ
  Lowest     Deferred queue     Software interrupts

When an event fires:
  1. Current statement finishes (not interrupted mid-calc)
  2. GOSUB pushes current position onto the stack
  3. Execution jumps to the handler
  4. Handler runs and ends with RETURN
  5. Execution resumes exactly where it left off

This is equivalent to a DOS TSR that chains INT 1Ch and performs
work in the background — but safely within the BASIC runtime.

1.2 Three-State Event Control

Every event source has three states, matching the GW-BASIC model:

  State   Effect
  -----   ---------------------------------------------------
  ON      Events fire immediately, handler is called
  OFF     Events are ignored, nothing queued
  STOP    Events are queued but not fired; when switched
          back to ON, queued events fire immediately

This allows you to "pause" events during critical sections
without losing them:

  10 TIMER STOP        ' Suspend timer during file write
  20 OPEN "DATA.DAT" FOR OUTPUT AS #1
  30 PRINT #1, DATA$
  40 CLOSE #1
  50 TIMER ON          ' Resume; queued timer events fire now

1.3 Event Nesting and Reentrancy

While an event handler is running, the same event will NOT fire
again (reentrancy guard via event_in_handler flag). This prevents
stack overflow from recursive timer ticks. Other event types CAN
still fire during a handler, giving you prioritized processing.

------------------------------------------------------------
2. Timer Events (ON TIMER)
------------------------------------------------------------

2.1 Basic Syntax

  ON TIMER(interval) GOSUB handler_line
  TIMER ON | OFF | STOP

The interval is in SECONDS and supports fractions:

  ON TIMER(1) GOSUB 5000     ' every 1 second
  ON TIMER(0.5) GOSUB 5000   ' every 500 ms
  ON TIMER(0.05) GOSUB 5000  ' every 50 ms (20 FPS)
  ON TIMER(300) GOSUB 5000   ' every 5 minutes

2.2 Clock Precision

BASIC++ uses clock() / CLOCKS_PER_SEC for timer resolution,
giving millisecond precision on most platforms. This is much
better than GW-BASIC's 18.2 Hz timer tick (55ms resolution).

  Minimum practical interval:  ~10ms (0.01 seconds)
  Maximum interval:            unlimited
  Typical game loop:           0.033 (30 FPS)
  Typical screensaver:         0.05 - 0.1 seconds
  Typical auto-save:           300 seconds (5 minutes)

2.3 Example: Background Clock

  10 REM Background clock in corner of screen
  20 ON TIMER(1) GOSUB 100
  30 TIMER ON
  40 REM ... main program runs normally ...
  50 PRINT "Working on main tasks..."
  60 FOR I = 1 TO 100
  70   PRINT I; " ";
  80   DELAY 200
  90 NEXT I
  95 END

  100 REM --- Timer Handler: Update Clock ---
  110 OC = CSRLIN: OP = POS(0)
  120 COLOR 14, 1
  130 LOCATE 1, 70
  140 PRINT TIME$;
  150 COLOR 7, 0
  160 LOCATE OC, OP
  170 RETURN

Key points:
  - Save cursor position (CSRLIN/POS) before drawing
  - Restore cursor position after drawing
  - RETURN continues the main program seamlessly

2.4 Example: Auto-Save TSR

  10 ON TIMER(120) GOSUB 900     ' auto-save every 2 min
  20 TIMER ON
  30 REM ... main editor program ...
  900 REM --- Auto-Save Handler ---
  910 TIMER STOP                  ' prevent re-entry
  920 LOCATE 25, 60
  930 COLOR 15, 2: PRINT " Saving... ";
  940 GOSUB 5000                  ' your save routine
  950 LOCATE 25, 60
  960 COLOR 7, 0: PRINT "           ";
  970 TIMER ON                    ' re-enable
  980 RETURN

2.5 The TICKS Function for Manual Timing

For situations where event-driven timing is too coarse or you
need elapsed-time measurement in your game loop:

  TICKS  — returns milliseconds since program start

  T1 = TICKS
  ' ... do work ...
  T2 = TICKS
  PRINT "Elapsed:"; T2 - T1; "ms"

Frame rate limiter pattern:

  100 GFT = TICKS               ' frame start
  ' ... render frame ...
  200 GT2 = TICKS
  210 ELAPSED = GT2 - GFT
  220 IF ELAPSED < 33 THEN DELAY 33 - ELAPSED   ' 30 FPS
  230 GFT = TICKS
  240 GOTO 100

3. Keyboard Events (ON KEY)
------------------------------------------------------------

3.1 Function Key Traps

  ON KEY(n) GOSUB handler_line
  KEY(n) ON | OFF | STOP

Key trap indices (GW-BASIC compatible):
  1-10   = F1 through F10
  11-12  = F11, F12
  13-16  = Arrow keys (Up, Down, Left, Right)
  17-20  = Reserved for extended keys

Example: F1 help overlay

  10 ON KEY(1) GOSUB 800
  20 KEY(1) ON
  30 REM ... main program ...

  800 REM --- F1 Help Handler ---
  810 DIM SAVEBUF(2000)
  820 SCREENSAVE 20, 5, 60, 20, SAVEBUF()
  830 BX1 = 20: BY1 = 5: BX2 = 60: BY2 = 20
  840 COLOR 15, 1
  850 LOCATE 5, 20
  860 FOR R = 5 TO 20
  870   LOCATE R, 20: PRINT STRING$(41, " ");
  880 NEXT R
  890 LOCATE 6, 25: PRINT "=== HELP ==="
  900 LOCATE 8, 22: PRINT "F1  = This help"
  910 LOCATE 9, 22: PRINT "ESC = Quit"
  920 LOCATE 18, 22: PRINT "Press any key..."
  930 K$ = "": WHILE K$ = "": K$ = INKEY$: WEND
  940 SCREENRESTORE SAVEBUF()
  950 RETURN

3.2 Reading Extended Keys with INKEY$

INKEY$ returns:
  ""           — no key pressed (non-blocking)
  1-char       — normal ASCII key
  2-char       — extended key: CHR$(0) + CHR$(scancode)

The 3-call pattern for arrow key detection:

  100 K$ = INKEY$
  110 IF K$ = "" THEN 100        ' no key
  120 IF LEN(K$) = 1 THEN 200   ' normal key
  130 REM Extended key
  140 SC = ASC(MID$(K$, 2, 1))
  150 IF SC = 72 THEN PRINT "Up"
  160 IF SC = 80 THEN PRINT "Down"
  170 IF SC = 75 THEN PRINT "Left"
  180 IF SC = 77 THEN PRINT "Right"
  190 IF SC = 71 THEN PRINT "Home"
  195 IF SC = 79 THEN PRINT "End"
  198 GOTO 100

  200 REM Normal key processing
  210 PRINT "Key: "; K$
  220 GOTO 100

Scan code reference:

  Key        Scan Code    Key         Scan Code
  --------   ---------    ---------   ---------
  Up         72           F1          59
  Down       80           F2          60
  Left       75           F3          61
  Right      77           F4          62
  Home       71           F5          63
  End        79           F6          64
  Page Up    73           F7          65
  Page Down  81           F8          66
  Insert     82           F9          67
  Delete     83           F10         68

4. Device I/O Events (VDev Layer)
------------------------------------------------------------

4.1 How Device Events Work

Virtual devices (VDev) with the VDCAP_EVENT capability are
polled by event_poll() on every statement. When a device's
dev_poll() function returns > 0, the registered handler fires.

This is equivalent to IRQ-driven I/O in hardware — the device
signals "data available" and the handler processes it.

4.2 COM Port Events

  ON COM(1) GOSUB 700
  COM(1) ON

When serial data arrives on COM1, line 700 fires.
Read the data with INPUT #n or GET #n.

4.3 USB Events

  MODULE "USB"
  ON STRIG(0) GOSUB 800     ' joystick/gamepad button
  STRIG(0) ON

USB HID devices (keyboards, mice, gamepads) generate events
through the STRIG mechanism when connected via the USB module.

------------------------------------------------------------
5. Mouse Events
------------------------------------------------------------

  ON MOUSE GOSUB handler_line
  MOUSE ON | OFF

  MOUSE(0) = button state (1=left, 2=right, 4=middle)
  MOUSE(1) = column (1-80)
  MOUSE(2) = row (1-25)
  MOUSE(3) = enabled (0 or 1)

Example: Mouse click handler

  10 ON MOUSE GOSUB 500
  20 MOUSE ON
  30 REM ... main program ...

  500 REM --- Mouse Handler ---
  510 IF MOUSE(0) = 1 THEN
  520   LOCATE MOUSE(2), MOUSE(1)
  530   COLOR 14, 0: PRINT "*";
  540 END IF
  550 RETURN

------------------------------------------------------------
6. Signal/Break Events
------------------------------------------------------------

  ON BREAK GOSUB handler_line

Intercept OS signals (Ctrl+C, SIGINT, SIGTERM):

  10 ON BREAK GOSUB 900
  20 PRINT "Running... press Ctrl+C to test"
  30 FOR I = 1 TO 1000000: NEXT I
  40 END

  900 REM --- Break Handler ---
  910 PRINT "Ctrl+C intercepted!"
  920 PRINT "Save data before exit? (Y/N)"
  930 K$ = "": WHILE K$ = "": K$ = INKEY$: WEND
  940 IF K$ = "Y" OR K$ = "y" THEN GOSUB 5000
  950 RETURN

7. Combining Events: The TSR Desktop Model
------------------------------------------------------------

A TUI desktop combines multiple event sources simultaneously,
exactly like a DOS TSR that hooks multiple interrupt vectors:

  10 REM === TUI Desktop with TSR-Style Events ===
  20 ON TIMER(1) GOSUB 5000       ' clock update
  30 ON KEY(1) GOSUB 5100         ' F1 = help
  40 ON KEY(10) GOSUB 5200        ' F10 = menu
  50 ON BREAK GOSUB 5300          ' Ctrl+C = safe exit
  60 TIMER ON: KEY(1) ON: KEY(10) ON
  70 REM Draw desktop...
  80 GOSUB 6000                   ' draw desktop
  90 REM === Idle loop (events fire between statements) ===
  100 K$ = INKEY$
  110 IF K$ <> "" THEN GOSUB 7000  ' process user input
  120 DELAY 10                     ' yield CPU
  130 GOTO 100

  5000 REM --- Clock TSR ---
  5010 LOCATE 1, 70: COLOR 14, 1
  5020 PRINT TIME$;
  5030 RETURN

  5100 REM --- F1 Help TSR ---
  5110 ' show help overlay
  5120 RETURN

  5200 REM --- F10 Menu TSR ---
  5210 ' show pull-down menu
  5220 RETURN

  5300 REM --- Break Handler ---
  5310 LOCATE 25, 1: COLOR 15, 4
  5320 PRINT " Really quit? (Y/N) ";
  5330 WHILE INKEY$ <> "Y": WEND
  5340 END

7.1 The Idle Loop Pattern

  100 K$ = INKEY$
  110 IF K$ <> "" THEN GOSUB HandleKey
  120 DELAY 10
  130 GOTO 100

This is the heart of every event-driven program:
  - INKEY$ checks for user input (non-blocking)
  - DELAY 10 yields 10ms to avoid 100% CPU usage
  - Between GOTO, DELAY, and INKEY$, all timer/key/device
    events get checked by event_poll()

7.2 Event Priority and Starvation

If your timer handler takes longer than the timer interval,
the next timer event is deferred until the handler returns.
Events don't "stack up" because the reentrancy guard prevents
the same event type from firing while its handler is active.

To avoid starvation:
  - Keep handlers short (< 50ms for 20 FPS games)
  - Use TIMER STOP during long operations
  - Check TICKS in handlers to skip frames if behind

8. Building a Text-Based Screensaver
------------------------------------------------------------

8.1 Architecture

A screensaver is a TIMER-driven animation that:
  1. Saves the current screen
  2. Runs an animation on a timer
  3. Restores the screen on any keypress

The TSR model makes this trivial:

  ON TIMER(idle_timeout) GOSUB StartScreensaver
  TIMER ON

Inside the screensaver:
  ON TIMER(frame_rate) GOSUB AnimateFrame
  TIMER ON
  WHILE INKEY$ = "": WEND     ' wait for any key
  TIMER OFF
  RestoreScreen

8.2 Screen Save/Restore

Use SCREENSAVE / SCREENRESTORE to capture and restore the
entire screen (or a region):

  DIM SCRBUF(2100)
  SCREENSAVE 1, 1, 80, 25, SCRBUF()
  ' ... screensaver runs ...
  SCREENRESTORE SCRBUF()

8.3 Integrating with a TUI Desktop

For a TUI desktop, the screensaver is an idle-timeout TSR:

  1. Main program sets: ON TIMER(300) GOSUB Screensaver
  2. Every keypress resets the idle counter
  3. When 5 minutes pass with no input, screensaver fires
  4. Any keypress dismisses and restores the desktop

  10 IDLE.MAX = 300             ' 5 minutes
  20 IDLE.COUNT = 0
  30 ON TIMER(1) GOSUB 8000     ' check idle every second
  40 TIMER ON

  8000 REM --- Idle Check TSR ---
  8010 IDLE.COUNT = IDLE.COUNT + 1
  8020 IF IDLE.COUNT >= IDLE.MAX THEN GOSUB 9000
  8030 RETURN

  In your key handler, reset the counter:
  7000 IDLE.COUNT = 0
  7010 ' ... process key ...
  7020 RETURN

8.4 The TRAP Three-Argument Form for TSRs

For DOS TSR-style direct event routing:

  TRAP event_class, source, handler_line

  TRAP 1, 0, 5000     ' TIMER event → line 5000
  TRAP 2, 1, 5100     ' KEY event, F1 → line 5100
  TRAP 7, 0, 5300     ' BREAK event → line 5300

This is equivalent to hooking specific interrupt vectors.

9. Complete Examples
------------------------------------------------------------

9.1 Clock TSR

  10 ON TIMER(1) GOSUB 100
  20 TIMER ON
  30 CLS: PRINT "Type anything. Clock updates in corner."
  40 INPUT "Your text: "; T$
  50 PRINT "You typed: "; T$
  60 GOTO 40

  100 OC = CSRLIN: OP = POS(0)
  110 COLOR 14, 1
  120 LOCATE 1, 68: PRINT " "; TIME$; " ";
  130 COLOR 7, 0
  140 LOCATE OC, OP
  150 RETURN

9.2 Activity Monitor TSR

  10 ON TIMER(0.5) GOSUB 100
  20 TIMER ON
  30 FOR I = 1 TO 10000
  40   REM ... work ...
  50 NEXT I
  60 END

  100 REM --- Activity Monitor ---
  110 LOCATE 25, 1: COLOR 0, 2
  120 PRINT " TICKS:"; INT(TICKS);
  130 PRINT " Free:"; FRE(0);
  140 PRINT "    ";
  150 COLOR 7, 0
  160 RETURN

9.3 Keyboard Macro TSR

  10 ON KEY(1) GOSUB 100    ' F1 = insert date
  20 ON KEY(2) GOSUB 200    ' F2 = insert signature
  30 KEY(1) ON: KEY(2) ON
  40 REM ... editor main loop ...

  100 REM --- F1: Insert Date ---
  110 PRINT DATE$;
  120 RETURN

  200 REM --- F2: Insert Signature ---
  210 PRINT "-- BASIC++ User";
  220 RETURN

------------------------------------------------------------
10. Advanced: Custom Event Sources
------------------------------------------------------------

10.1 User-Defined Events via CAUSE

  CAUSE EXCEPTION n    ' fires ON ERROR / ON TRAP(0) handler

This is the BASIC equivalent of a software interrupt (INT n).
Your program can define custom event codes and trigger them.

10.2 VDev Custom Devices

Register a custom VDev with VDCAP_EVENT capability, and its
dev_poll() function will be called by event_poll() automatically.
When dev_poll() returns > 0, the ON DEVICE handler fires.

This is the extensibility point for adding new hardware or
software event sources to BASIC++.
