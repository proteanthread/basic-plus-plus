=====================================================================
1.  INTRODUCTION
=====================================================================

This document describes the internal architecture of the BASIC++
interpreter.  It is written for programmers who want to:

  * Understand how BASIC++ processes and executes programs
  * Add new statements, functions, or subsystems
  * Port BASIC++ to a new platform
  * Debug interpreter behavior at the C level
  * Write dialect or module plug-ins

BASIC++ is written in strict ANSI C89/C90 with zero external
dependencies (not even POSIX).  The entire interpreter compiles to
a single executable of approximately 346 KB.

Design principles:

  1. SINGLE RESPONSIBILITY -- Each .c/.h pair owns exactly one
     subsystem.  No module calls malloc() directly except memory.c.
  2. EXPLICIT STATE -- All mutable interpreter state lives in the
     RuntimeState struct on the heap.  Nothing hides on the C stack.
  3. NO LONGJMP -- Errors use a global flag, not setjmp/longjmp.
     Every function checks the flag and returns early.
  4. PHASE-BASED EVOLUTION -- The codebase grew in numbered phases.
     Comments like "Phase 4" or "Phase 16" mark when a feature was
     added.  These are historical markers, not runtime phases.

2.  SOURCE FILE MAP
=====================================================================

The interpreter is organized into the following compilation units.
Each .h file contains the public interface; the matching .c file
contains the implementation.

  CORE PIPELINE
  -------------
  main.c            Entry point, REPL loop, bootstrap sequence
  lexer.h/.c        Tokenizer (source text -> token stream)
  parser.h/.c       Recursive-descent parser (parse-and-execute)
  exec.h/.c         Program executor (RUN, CONT, sequential walk)
  runtime.h/.c      Interpreter state (variables, stack, position)

  DATA & MEMORY
  -------------
  config.h          Compile-time constants and limits
  memory.h/.c       Memory pools and program line storage
  value.h/.c        Tagged union value type (int/float/string)
  stringpool.h/.c   Bump-allocated string storage

  SUBSYSTEMS
  ----------
  errors.h/.c       Three-level error model (WHAT/HOW/SORRY)
  dialect.h/.c      Dialect definitions and runtime switching
  funcreg.h/.c      Central function/keyword registry
  vdev.h/.c         Virtual device layer (VDev2)
  module.h/.c       Plug-in module system
  security.h/.c     Sandboxing and capability gating
  fileio.h/.c       File channel I/O (#1 through #8)
  platform.h/.c     OS/compiler detection
  help.h/.c         Built-in HELP command database
  gfxbuf.h/.c       Graphics framebuffer (SCREEN/DRAW)
  memmap.h/.c       Virtual memory maps (MSDOS, C64, etc.)
  selftest.h/.c     Built-in self-test framework (SELFTEST)
  detok.h/.c        Detokenizer (token -> source text)

  COMPILER (OPTIONAL)
  -------------------
  ast.h/.c          Abstract syntax tree (compiler only)
  compiler.h/.c     Transpiler front-end (BASIC -> C89)
  codegen.h/.c      C89 code generation back-end
  bytecode.h/.c     Bytecode format definitions

  MODULES
  -------
  mod_stdlib.h/.c   Standard library module
  mod_usb.h/.c      USB device module
  builtins.h/.c     Built-in function implementations

  VM
  ---
  vm.h/.c           Opcode dispatch table and eval stack


=====================================================================
3.  BOOT SEQUENCE
=====================================================================

When BASIC++ starts, main() executes a precise initialization
sequence.  Each step depends on the ones before it.  The order
is not arbitrary -- changing it will cause crashes or silent
corruption.

The full boot sequence (main.c, lines 138-191):

  Step  Function Call              What It Does
  ----  ------------------------  --------------------------------
   1    printf(banner)            Print version and copyright
   2    mem_init(&memory)         Allocate all memory pools
   3    platform_init()           Detect OS, compiler, CPU
   4    dialect_init(TINY_BASIC)  Set default dialect
   5    vdev_init()               Initialize virtual device table
   6    funcreg_init()            Build function registry
   7    security_init(SEC_OPEN)   Set default security level
   8    module_system_init()      Initialize module infrastructure
   9    mod_stdlib_register()     Register standard library module
  10    mod_usb_register()        Register USB module (inactive)
  11    module_activate("STDLIB") Activate standard library
  12    dialect_apply()           Apply dialect-specific overrides
  13    fileio_channels_init()    Open file channel table
  14    vm_init()                 Build VM opcode dispatch table
  15    gfxbuf_init()             Clear graphics framebuffer
  16    runtime_init(&rt,...)     Initialize RuntimeState to zero

After step 16, the interpreter prints "Ready." and enters the
REPL loop.

WHY THIS ORDER MATTERS:

  * mem_init() must come first because every other subsystem
    allocates from the pools it creates.

  * platform_init() must precede dialect_init() because some
    dialect behaviors depend on the detected platform (e.g.,
    line endings, path separators).

  * funcreg_init() must follow dialect_init() so that the
    registry knows which keyword set is active.

  * module_activate() must follow mod_stdlib_register() -- you
    cannot activate a module that hasn't been registered.

  * dialect_apply() must follow both funcreg_init() and
    module_activate() because it patches the registry with
    dialect-specific overrides.

  * runtime_init() must come last because it wires up pointers
    to the memory system, program store, and VDev layer, all
    of which must already be initialized.

If you add a new subsystem, insert its init call at the
appropriate point in this sequence and document the dependency.


=====================================================================
4.  MEMORY SYSTEM (memory.h / memory.c)
=====================================================================

BASIC++ uses a three-pool memory architecture.  After the initial
malloc() calls in mem_init(), no further heap allocation occurs
during normal operation.  This makes the interpreter predictable
and safe for embedded or constrained environments.

  +-------------------------------+
  |  ProgramStore                 |  Array of ProgramLine structs
  |  (MAX_PROGRAM_LINES entries)  |  Sorted by line number
  +-------------------------------+
  |  Variable Pool (64K)          |  A-Z variables, @() array,
  |                               |  named variables, DIM arrays
  +-------------------------------+
  |  Scratch Pool (64K)           |  Temporary buffers, reset
  |                               |  after every statement
  +-------------------------------+

4.1  MemoryPool

  Each pool is a flat byte array with bump allocation:

    typedef struct MemoryPool {
        char *base;    /* start of allocated block */
        long  size;    /* total capacity in bytes  */
        long  used;    /* current watermark        */
    } MemoryPool;

  Allocation advances 'used'; there is no individual free().
  The scratch pool is reset (used = 0) between every statement.
  The variable pool is reset only on NEW or RUN.

  Functions:
    mem_pool_alloc(pool, nbytes)  - bump-allocate from pool
    mem_pool_reset(pool)          - reset watermark to zero
    mem_pool_available(pool)      - bytes remaining

4.2  ProgramStore

  Program lines are stored as an array of ProgramLine structs,
  kept sorted by line_number at all times:

    typedef struct ProgramLine {
        int  line_number;
        char text[MAX_LINE_LENGTH + 1];
    } ProgramLine;

  The array is binary-searched for GOTO targets (program_find)
  and sequentially walked during RUN (program_find_next).

  Key insight: lines are stored as raw source text.  LIST and
  SAVE reproduce them verbatim.  No tokenization or compression
  is applied to stored lines -- the lexer re-tokenizes each
  line every time it executes.

  Functions:
    program_insert(store, line_num, text)  - insert or replace
    program_delete(store, line_num)        - remove a line
    program_find(store, line_num)          - binary search (exact)
    program_find_next(store, line_num)     - find >= target
    program_clear(store)                   - NEW command
    program_list(store, from, to)          - LIST command

4.3  MemorySystem

  The top-level container owns both pools and the program store:

    typedef struct MemorySystem {
        MemoryPool   variable;
        MemoryPool   scratch;
        ProgramStore program;
    } MemorySystem;

  This struct is stack-allocated in main() and passed by pointer
  to runtime_init().  The RuntimeState holds a borrowed pointer
  to it (not a copy).


=====================================================================
5.  THE VALUE SYSTEM (value.h / value.c)
=====================================================================

All data in BASIC++ flows through the BValue tagged union.
Variables, DATA items, expression results, and function return
values are all BValues.

  typedef enum ValueType {
      VAL_INTEGER = 0,   /* long integer             */
      VAL_FLOAT,         /* double precision float    */
      VAL_STRING         /* pointer into string pool  */
  } ValueType;

  typedef struct BValue {
      ValueType type;
      union {
          long   ival;         /* VAL_INTEGER */
          double fval;         /* VAL_FLOAT   */
          struct {
              char *data;      /* borrowed pointer */
              int   length;    /* byte count       */
          } sval;              /* VAL_STRING  */
      } v;
  } BValue;

5.1  Constructors

  bval_int(42)             -> BValue { type=VAL_INTEGER, v.ival=42 }
  bval_float(3.14)         -> BValue { type=VAL_FLOAT, v.fval=3.14 }
  bval_string(ptr, len)    -> BValue { type=VAL_STRING, v.sval=... }

5.2  Type Coercion

  Arithmetic operations coerce operands automatically:

    INT op INT    -> INT result (long arithmetic)
    INT op FLOAT  -> INT promoted to FLOAT, FLOAT result
    FLOAT op INT  -> same as above
    FLOAT op FLOAT -> FLOAT result

  String-to-number coercion uses VAL() semantics (parse leading
  digits, return 0 on failure).  Number-to-string coercion uses
  STR$() semantics.

5.3  String Ownership

  CRITICAL: BValue does NOT own string data.  The .sval.data
  pointer borrows into the string pool (see section 6).  This
  means:

    * No per-value malloc/free
    * No reference counting
    * String data is valid only until the pool is reset
    * Concatenation allocates a new pool entry; the old
      fragments are not individually freed

  This design matches classic BASIC interpreters (Microsoft BASIC,
  Applesoft) where string garbage collection was a single bulk
  operation, not per-string.


=====================================================================
6.  STRING POOL (stringpool.h / stringpool.c)
=====================================================================

String data is stored in a bump-allocated pool:

  typedef struct StringPool {
      char *buffer;         /* pool base */
      int   capacity;       /* total bytes */
      int   used;           /* current watermark */
  } StringPool;

  stringpool_alloc(pool, len)   - allocate len bytes, return ptr
  stringpool_reset(pool)        - reset watermark to zero

The pool lives inside RuntimeState (field: strpool).  It is
reset on RUN, NEW, and CLEAR.

Every string operation (concatenation, MID$, LEFT$, etc.)
allocates fresh space in the pool.  The old fragments remain
until the next reset.  This means string-heavy programs can
exhaust the pool within a single RUN.  The SIZE function reports
remaining pool space.

Design trade-off: bump allocation is extremely fast (one pointer
increment) but wastes space on dead strings.  For the target
workloads (short BASIC programs on retro hardware), this is
the right trade-off.  A compacting GC would be more space-
efficient but violates the "no hidden pauses" design goal.


=====================================================================
7.  THE LEXER (lexer.h / lexer.c)
=====================================================================

The lexer converts source text into a stream of Token structs.

7.1  Token Types

  Atoms:       TOK_NUMBER, TOK_FLOAT_LIT, TOK_STRING,
               TOK_VARIABLE (A-Z), TOK_STRING_VAR (A$-Z$),
               TOK_NAMED_VAR (multi-character)

  Keywords:    TOK_KEYWORD (with a KeywordId sub-tag)

  Operators:   TOK_PLUS, TOK_MINUS, TOK_STAR, TOK_SLASH,
               TOK_EQUALS, TOK_LT, TOK_GT, TOK_LT_EQ,
               TOK_GT_EQ, TOK_NOT_EQ, TOK_CARET, TOK_BACKSLASH,
               TOK_PIPE, TOK_APPEND

  Delimiters:  TOK_LPAREN, TOK_RPAREN, TOK_COMMA, TOK_SEMICOLON,
               TOK_COLON, TOK_HASH, TOK_AT

  Control:     TOK_CR (end of line), TOK_EOF (end of input)

7.2  Keyword Table

  The lexer maintains a static table of keyword strings mapped to
  KeywordId values.  When the lexer encounters an alphabetic
  sequence, it checks the keyword table (case-insensitive).  If a
  match is found, the token is TOK_KEYWORD with the corresponding
  KeywordId.  Otherwise, it's a variable name.

  The keyword table is dialect-aware: dialect_apply() can modify
  which keywords are active.  Disabled keywords fall through to
  variable names, enabling programs written for one dialect to
  use keywords from another dialect as variable names.

7.3  Zero-Copy Strings

  String literal tokens (TOK_STRING) point directly into the
  source buffer.  The lexer does not copy string data.  This
  means the source buffer must remain valid for the lifetime of
  the token.  Since BASIC++ re-lexes each line on every execution,
  the source buffer (the ProgramLine.text field) is always
  available.

7.4  Usage Pattern

    Lexer lex;
    lexer_init(&lex, source_text);
    lexer_next(&lex);       /* advance to first token */

    while (lex.current.type != TOK_EOF) {
        /* process lex.current */
        lexer_next(&lex);   /* advance */
    }


=====================================================================
8.  THE PARSER (parser.h / parser.c)
=====================================================================

The parser is a large recursive-descent module (parser.c is the
biggest file in the project at ~400 KB).  It uses the PARSE-AND-
EXECUTE model: there is no intermediate representation between
parsing and execution in the interpreter path.

8.1  Parse-and-Execute Model

  When the parser encounters a PRINT statement:

    1. It recognizes TOK_KEYWORD with KW_PRINT
    2. It calls parse_print()
    3. parse_print() evaluates expressions inline
    4. The result is printed immediately
    5. Control returns to the caller

  There is no AST, no bytecode, and no separate execution phase
  for the interpreter path.  The parser IS the executor for
  individual statements.

  This model is identical to how Microsoft GW-BASIC, Applesoft
  BASIC, and Palo Alto Tiny BASIC work.  It's simple, fast for
  small programs, and extremely memory-efficient.

8.2  Expression Evaluation

  Expressions are parsed by recursive descent with standard
  operator precedence:

    Level 0:  OR
    Level 1:  AND
    Level 2:  NOT
    Level 3:  Comparisons  (=, <, >, <=, >=, <>)
    Level 4:  Addition     (+, -)
    Level 5:  Multiply     (*, /, \, MOD)
    Level 6:  Exponent     (^)
    Level 7:  Unary        (-, +, NOT)
    Level 8:  Atoms        (numbers, variables, functions, parens)

  Each level calls the next higher level for its operands.  This
  naturally implements correct precedence and associativity.

8.3  Statement Dispatch

  The main parser entry point reads the first token and dispatches
  to the appropriate parse_xxx() function based on the KeywordId:

    KW_PRINT  -> parse_print()
    KW_LET    -> parse_let()
    KW_GOTO   -> parse_goto()
    KW_IF     -> parse_if()
    KW_FOR    -> parse_for()
    ...

  If the first token is a variable name (no keyword), the parser
  assumes an implicit LET statement (assignment).


=====================================================================
9.  THE EXECUTOR (exec.h / exec.c)
=====================================================================

The executor handles multi-line program execution (RUN, CONT).
It is a simple sequential walker over the ProgramStore.

9.1  The exec_run() Loop

  The core execution loop is straightforward:

    1. Set runtime.current_index = 0 (or resume point)
    2. Set runtime.running = 1
    3. While running and current_index < program.count:
       a. Get current line text
       b. Initialize lexer on that text
       c. Skip past the line number tokens
       d. Call the parser to execute the statement(s)
       e. Check for errors -> if error, stop
       f. Advance: if next_index was set (GOTO/GOSUB),
          use it; otherwise, current_index++
    4. Set runtime.running = 0

  The next_index field is the flow-control mechanism.  GOTO sets
  next_index to the target line's program store index.  GOSUB
  pushes a return frame and sets next_index.  RETURN pops the
  frame and restores next_index.  If no flow control occurs,
  next_index remains -1 and the executor auto-advances.

9.2  Multi-Statement Lines

  BASIC++ supports multiple statements on one line, separated by
  colons:

    10 PRINT "A" : PRINT "B" : PRINT "C"

  The parser handles this internally.  After executing one
  statement, it checks for TOK_COLON.  If found, it consumes the
  colon and parses the next statement.  The executor sees this as
  a single line.


=====================================================================
10. RUNTIME STATE (runtime.h / runtime.c)
=====================================================================

The RuntimeState struct is the heart of the interpreter.  It
contains ALL mutable state during program execution.  Nothing
is stored in C global variables or on the C stack (except
temporary locals within functions).

10.1  Core Fields

  program         Pointer to ProgramStore (borrowed)
  memory          Pointer to MemorySystem (borrowed)
  running         1 if executing a program, 0 if at prompt
  current_index   Index of the currently executing line
  next_index      Next line index (-1 = auto-advance)
  stopped         1 if STOP or END was executed

10.2  Variable Storage

  variables[26]       Single-letter vars A-Z (BValue)
  string_vars[26]     String vars A$-Z$ (BValue)
  named_vars[256]     Multi-character named variables
  named_count         Number of named vars defined
  dim_arrays[64]      DIMmed arrays (1D and 2D)
  dim_count           Number of DIM arrays defined
  dim_elements[8192]  Flat pool for array elements
  dim_elements_used   Elements allocated from pool

10.3  Flow Control

  stack[256]          Unified stack frames (GOSUB/FOR/WHILE/DO/SUB)
  stack_top           Stack pointer (0 = empty)

  The stack uses a unified StackFrame type with a FrameType
  discriminator:

    FRAME_GOSUB   Return address for GOSUB
    FRAME_FOR     FOR/NEXT loop state (var, limit, step, body)
    FRAME_WHILE   WHILE/WEND loop (loop-back index)
    FRAME_DO      DO/LOOP loop (body index, UNTIL/WHILE flag)
    FRAME_SUB     SUB/FUNCTION call (return addr, saved vars)

10.4  Subsystem State

  strpool             String pool (bump allocator)
  dev_con, dev_err    Console and error VDev pointers
  trace_on            TRON/TROFF flag
  on_error_line       ON ERROR GOTO target (0 = disabled)
  last_err_code       ERR value
  last_err_line       ERL value
  user_funcs[64]      DEF FN definitions
  user_func_count     Count of defined user functions
  eval_items[128]     VM expression evaluation stack
  eval_top            Eval stack pointer
  breakpoints[32]     Debugger breakpoint lines
  breakpoint_count    Number of active breakpoints
  single_step         Debugger single-step mode

10.5  Screen State

  screen_mode         Current SCREEN mode (0=text)
  draw_x, draw_y      DRAW cursor position
  draw_color          DRAW pen character
  cursor_row          CSRLIN value (1-based)
  cursor_col          POS(0) value (1-based)
  screen_width        WIDTH columns (40 or 80)
  screen_lines        Screen height (default 25)

10.6  Other State

  rnd_seed            RND seed (deterministic PRNG)
  auto_line           AUTO mode next line number
  auto_step           AUTO mode increment
  constants[64]       CONST table
  subs[64]            SUB/FUNCTION definitions
  labels[128]         Line label table
  mem_segment[64K]    Virtual memory (PEEK/POKE)
  mem_seg_base        DEF SEG base address
  memmap_type         Active memory map preset
  user_types[32]      TYPE...END TYPE definitions
  typed_vars[64]      Typed variable instances
  fkey_macros[48]     Function key macro strings
  fkey_display        KEY ON/OFF flag

10.7  Initialization and Reset

  runtime_init(rt, program, memory)
    Called once at startup.  Zeros everything, wires up
    borrowed pointers, configures defaults.

  runtime_reset(rt)
    Called on RUN and NEW.  Clears all variables, resets
    the stack, resets the string pool, resets DATA pointer.
    Does NOT clear the program store.


=====================================================================
11. THE STACK MACHINE
=====================================================================

BASIC++ uses a bounded, type-checked stack for flow control.
The stack depth is MAX_STACK_DEPTH (256 frames).

11.1  Pushing

  int runtime_push(RuntimeState *rt, const StackFrame *frame);

  Returns 0 on success.  Returns -1 and raises ERR_SORRY if the
  stack is full.

11.2  Popping

  int runtime_pop(RuntimeState *rt, FrameType expected,
                  StackFrame *out);

  Pops the top frame and verifies that its type matches
  'expected'.  If the stack is empty or the types don't match,
  raises ERR_HOW and returns -1.

  This type checking prevents common BASIC errors:
    * RETURN without GOSUB
    * NEXT without matching FOR
    * WEND without matching WHILE

11.3  Stack Frame Union

  typedef struct StackFrame {
      FrameType type;
      union {
          struct { int return_index; } gosub;
          struct { char var_name; long limit;
                   long step; int body_index; } for_loop;
          struct { int loop_index; } while_loop;
          struct { int body_index; int is_until;
                   int is_pre; } do_loop;
          struct { int return_index; int sub_index;
                   BValue saved_vars[26];
                   BValue saved_strvars[26]; } sub_call;
      } data;
  } StackFrame;

  Note: SUB call frames save the entire variable set.  This
  provides true local scoping by snapshot-and-restore (the same
  technique used by Dartmouth BASIC and GW-BASIC for DEF FN).


=====================================================================
12. ERROR HANDLING (errors.h / errors.c)
=====================================================================

BASIC++ uses the classic Tiny BASIC three-level error model:

  WHAT?   Syntax error (malformed statement or expression)
  HOW?    Runtime error (bad line number, division by zero,
          type mismatch, stack underflow)
  SORRY.  Resource error (out of memory, stack overflow,
          too many program lines)

12.1  Error Flow

  Errors are NON-FATAL.  They do not use longjmp, exceptions,
  or stack unwinding.  Instead:

    1. A module calls error_raise(ERR_HOW, line_number).
    2. error_raise() prints the message (e.g., "HOW? AT LINE 50")
       and sets a global error flag.
    3. The calling function checks error_occurred() and returns
       early (propagating up the call chain).
    4. The REPL loop or exec_run() detects the error and prints
       "Ready." to return to the prompt.
    5. error_clear() resets the flag before processing the next
       input.

  This means EVERY function in the parser and executor must check
  error_occurred() after calling any sub-function.  Failure to
  check leads to undefined behavior (continuing execution after
  an error).

12.2  Extended Error Info

  ERR    Returns the last error code (1=WHAT, 2=HOW, 3=SORRY)
  ERL    Returns the line number where the last error occurred

  These are stored in RuntimeState fields last_err_code and
  last_err_line.  They are set by error_raise() and persist
  until the next error or CLEAR.

12.3  ON ERROR GOTO

  The structured error handler allows programs to trap errors:

    ON ERROR GOTO 1000
    ...code that might error...
    ON ERROR GOTO 0        ' disable handler

  When an error occurs with ON ERROR active, instead of printing
  the error and returning to the prompt, execution jumps to the
  target line.  The program can inspect ERR and ERL, then RESUME
  or RESUME NEXT.

12.4  Adding New Error Codes

  Currently, all errors map to one of three codes.  To add a
  more specific error (e.g., ERR_FILE_NOT_FOUND):

    1. Add the code to the ErrorCode enum in errors.h
    2. Add the display string to error_message() in errors.c
    3. The existing error_raise/error_occurred/error_clear
       mechanism works unchanged


=====================================================================
13. VIRTUAL DEVICES (vdev.h / vdev.c)
=====================================================================

The Virtual Device layer (VDev2) provides a uniform I/O
abstraction.  All device interaction -- console, files, serial
ports, network sockets -- flows through the same interface.

13.1  Device Structure

  typedef struct VDev {
      char        name[VDEV_MAX_NAME];
      VDevClass   dev_class;
      unsigned    caps;        /* capability flags */
      int         active;
      VDevRead    fn_read;     /* function pointers */
      VDevWrite   fn_write;
      VDevOpen    fn_open;
      VDevClose   fn_close;
      VDevStatus  fn_status;
      VDevIoctl   fn_ioctl;
      void       *user_data;   /* opaque state */
  } VDev;

13.2  Device Classes

  VDEV_CLASS_CONSOLE    Terminal / screen
  VDEV_CLASS_FILE       Disk file
  VDEV_CLASS_SERIAL     RS-232 / USB serial
  VDEV_CLASS_NETWORK    TCP/UDP socket
  VDEV_CLASS_HID        USB HID (gamepad, joystick)
  VDEV_CLASS_AUDIO      Sound device
  VDEV_CLASS_VIDEO      Video / framebuffer
  VDEV_CLASS_CUSTOM     User-defined

13.3  Capability Flags

  VDEV_CAP_READ     Device can be read from
  VDEV_CAP_WRITE    Device can be written to
  VDEV_CAP_SEEK     Device supports random access
  VDEV_CAP_BINARY   Device supports binary mode
  VDEV_CAP_IOCTL    Device supports control commands
  VDEV_CAP_STATUS   Device can report status

13.4  Device Table

  The system maintains a global table of up to 64 device slots.
  Three devices are built-in and always present:

    Slot 0: CON:    Console (stdin/stdout)
    Slot 1: ERR:    Error output (stderr)
    Slot 2: FILE:   Generic file device

  Additional devices are registered by modules (e.g., mod_usb
  registers USB HID and USB serial devices).

13.5  BASIC Interface

  From BASIC, devices are accessed through:

    OPEN "CON:" FOR INPUT AS #1    ' open console for reading
    INP(device_id)                 ' read byte from device
    OUT device_id, byte            ' write byte to device
    VDEV LIST                      ' list registered devices
    VDEV STATUS device_id          ' query device status
    VDEV IOCTL device_id, cmd, val ' send control command

13.6  Adding a New Device

  To add a custom device:

    1. Write fn_read, fn_write, fn_open, fn_close functions
    2. Call vdev_register() with name, class, caps, and function
       pointers
    3. The device becomes accessible from BASIC immediately
    4. Security gating is automatic (restricted mode blocks
       device access)

14. FUNCTION REGISTRY (funcreg.h / funcreg.c)
=====================================================================

The function registry is the central dispatch table for all
built-in functions, statements, and operators.

14.1  Function Entry

  typedef struct FunctionEntry {
      char         name[MAX_FUNC_NAME];
      int          name_len;
      FuncType     type;        /* FUNC_NUMERIC, FUNC_STRING, etc. */
      int          min_args;
      int          max_args;
      FuncHandler  handler;     /* C function pointer */
      unsigned     flags;       /* dialect, security flags */
      int          dialect_mask; /* which dialects enable this */
  } FunctionEntry;

14.2  How It Works

  When the parser encounters a function call (e.g., LEN("HELLO")),
  it looks up "LEN" in the registry.  The registry returns the
  matching FunctionEntry, which contains:

    * The C handler function to call
    * Argument count validation (min/max)
    * Type information (returns numeric or string?)
    * Dialect mask (is this function available in the current
      dialect?)
    * Security level (is this function allowed at the current
      trust level?)

  If the function is disabled by the current dialect or security
  level, the lookup returns NULL and the parser raises ERR_WHAT.

14.3  Dialect Overrides

  When dialect_apply() runs, it walks the registry and patches
  entries based on the active dialect's configuration.  This
  allows:

    * Disabling functions (QBasic has no INP/OUT in Tiny mode)
    * Changing function behavior (PRINT differences between
      dialects)
    * Adding dialect-specific extensions (CoCo BASIC extras)

14.4  Registering New Functions

  Modules register functions via:

    funcreg_register(name, type, min, max, handler, flags)

  The handler function has the signature:

    BValue my_func(RuntimeState *rt, BValue *args, int argc);

15. DIALECT ENGINE (dialect.h / dialect.c)
=====================================================================

BASIC++ can emulate multiple BASIC dialects at runtime.  The
dialect engine controls which keywords, functions, and behaviors
are active.

15.1  Available Dialects

  DIALECT_TINY_BASIC     Palo Alto Tiny BASIC (default)
  DIALECT_GWBASIC        Microsoft GW-BASIC / BASICA
  DIALECT_QBASIC         Microsoft QBasic / QuickBASIC
  DIALECT_COCO           TRS-80 Color Computer BASIC
  DIALECT_DARTMOUTH      Dartmouth BASIC (original)
  DIALECT_BASICPP        BASIC++ extended dialect

15.2  DialectConfig

  Each dialect is defined by a DialectConfig struct that specifies:

    * Keyword table (which keywords are recognized)
    * Statement set (which statements are available)
    * Function set (which built-in functions are available)
    * Behavior flags (line number requirements, LET keyword
      requirement, array base, string handling mode, etc.)
    * Memory layout (variable types, string length limits)

15.3  Runtime Switching

  The DIALECT command switches dialects at runtime:

    DIALECT QBASIC     ' switch to QBasic mode

  This calls dialect_init() followed by dialect_apply(), which
  reconfigures the lexer's keyword table, the function registry,
  and various runtime behaviors.  The program store is preserved --
  only the execution environment changes.

15.4  Behavior Differences

  Some key differences between dialects:

  Feature           Tiny    GW-BASIC   QBasic     BASIC++
  -------           ----    --------   ------     -------
  Line numbers      Req'd   Req'd      Optional   Optional
  LET keyword       Req'd   Optional   Optional   Optional
  String variables  No      A$-Z$      Named      Named
  Named variables   No      No         Yes        Yes
  SUB/FUNCTION      No      No         Yes        Yes
  TYPE...END TYPE   No      No         Yes        Yes
  Array base        0       0/1        0/1        0/1
  Max line#         32767   65529      None       32767

16. MODULE SYSTEM (module.h / module.c)
=====================================================================

Modules are plug-in packages that extend BASIC++ with new
functions, statements, and device drivers.

16.1  Module Lifecycle

    mod_xxx_register()     Register the module (make it known)
    module_activate(name)  Activate it (load functions/devices)
    module_deactivate(name) Deactivate (unload, optional)

  Registration makes the module's name and metadata available.
  Activation calls the module's init function, which registers
  functions in the function registry and devices in the VDev
  table.

16.2  Built-In Modules

  STDLIB    Standard library (always active)
            Math, string, and utility functions
  USB       USB device support (activate with MODULE LOAD "USB")
            HID gamepads, serial ports, device enumeration

16.3  Module API

  A module provides:

    * A register function (called at boot)
    * An init function (called on activation)
    * A shutdown function (called on deactivation)
    * An array of FunctionEntry structs to register
    * An array of VDev definitions to register

16.4  Writing a New Module

  See External_Modules.txt for a complete tutorial on creating
  custom modules.  The minimum requirement is:

    1. Create mod_xxx.h with a register function prototype
    2. Create mod_xxx.c implementing register, init, and
       at least one function handler
    3. Add mod_xxx_register() to main.c's boot sequence
    4. Add mod_xxx.c to the Makefile


=====================================================================
17. SECURITY MODEL (security.h / security.c)
=====================================================================

BASIC++ implements a three-tier security model that controls
what operations programs can perform.

17.1  Security Levels

  SEC_OPEN        No restrictions (default)
                  All operations allowed
  SEC_STANDARD    Moderate restrictions
                  File I/O limited to current directory
                  SHELL disabled
                  Network access limited
  SEC_RESTRICTED  Maximum restrictions
                  No file I/O
                  No SHELL
                  No network
                  No device access
                  No module loading

17.2  Capability Gating

  Security is enforced at the function registry level.  Each
  FunctionEntry has a security flag that specifies the minimum
  trust level required.  When a function is called, the registry
  checks the current security level before dispatching.

  This means security is transparent to the parser -- it doesn't
  need to know about security at all.  The registry handles it.

17.3  Changing Security Level

  From BASIC:
    SECURITY OPEN           ' no restrictions
    SECURITY STANDARD       ' moderate restrictions
    SECURITY RESTRICTED     ' maximum restrictions

  Once RESTRICTED is set, it cannot be lowered from BASIC code
  (only from the command line or by restarting the interpreter).
  This prevents untrusted programs from escalating privileges.

18. VM DISPATCH LAYER (vm.h / vm.c)
=====================================================================

The VM module provides a transition layer between the current
parse-and-execute interpreter and a future bytecode-compiled
execution engine.

18.1  Current Role

  In the current interpreter, the VM provides:

    * An opcode dispatch table (for future bytecode)
    * An expression evaluation stack (eval_items/eval_top)
    * State machine hooks (VM_IDLE, VM_RUNNING, VM_PAUSED, etc.)

  The expression evaluation stack is used by some built-in
  functions and the compiler subsystem.  The main interpreter
  path still uses recursive descent (not the eval stack).

18.2  Eval Stack

  The eval stack is a fixed-size array of BValue items:

    BValue eval_items[VM_EVAL_STACK_SIZE];  /* 128 entries */
    int    eval_top;                        /* -1 = empty  */

  Push/pop operations are used for postfix expression evaluation
  in the compiler path.  The interpreter path uses C function
  calls for expression evaluation instead.

18.3  VM States

  VM_IDLE       Not executing (at REPL prompt)
  VM_RUNNING    Executing a program (RUN)
  VM_PAUSED     Paused (STOP, breakpoint)
  VM_ERROR      Error state (after unhandled error)

18.4  Future Direction

  The VM module is designed to grow into a full bytecode virtual
  machine.  The bytecode.h file defines opcode formats, and
  codegen.c can generate bytecode from ASTs.  However, the
  bytecode execution path is not yet connected to the main
  interpreter -- it exists as scaffolding for future phases.

19. COMPILER / TRANSPILER (compiler.h / ast.h / codegen.h)
=====================================================================

BASIC++ includes an optional compiler that can transpile BASIC
source code to ANSI C89, which can then be compiled to a native
executable.

19.1  Compiler Pipeline

  BASIC source
      |
      v
  Lexer (lexer.h)      -- tokenize
      |
      v
  Parser (ast.h)        -- build AST (NOT parse-and-execute)
      |
      v
  AST (ast.h)           -- abstract syntax tree
      |
      v
  Codegen (codegen.h)   -- emit C89 source code
      |
      v
  C89 source file       -- compile with cc/gcc/cl

19.2  AST vs. Interpreter

  IMPORTANT: The AST module (ast.h/ast.c) is used ONLY by the
  compiler path.  The interpreter does NOT build an AST.  The
  parser in interpreter mode uses parse-and-execute (direct
  evaluation during parsing).

  The AST is a tree of ASTNode structs:

    typedef struct ASTNode {
        ASTNodeType type;       /* statement, expression, etc. */
        /* child pointers, value data, etc. */
    } ASTNode;

  AST node types include:
    AST_PROGRAM, AST_LINE, AST_PRINT, AST_LET, AST_GOTO,
    AST_IF, AST_FOR, AST_WHILE, AST_LITERAL_INT,
    AST_LITERAL_FLOAT, AST_LITERAL_STRING, AST_VARIABLE,
    AST_BINARY_OP, AST_UNARY_OP, AST_FUNC_CALL, etc.

19.3  Code Generation

  The code generator (codegen.c) walks the AST and emits C89
  source code.  It maps BASIC constructs to C equivalents:

    BASIC               C89
    -----               ---
    PRINT "hello"       printf("hello\n");
    LET X = 42          vars[23] = bval_int(42);
    GOTO 100            goto line_100;
    FOR I = 1 TO 10     for (vars[8]=bval_int(1); ...
    IF X > 0 THEN ...   if (bval_to_int(&vars[23]) > 0) { ...

  See Compiling_BASIC_Programs.txt for user-facing documentation.

20. PLATFORM ABSTRACTION (platform.h / platform.c)
=====================================================================

The platform module detects the host environment at startup and
provides conditional behavior for platform-specific operations.

20.1  Detection

  platform_init() detects:

    * Operating system (Windows, Linux, macOS, FreeDOS, etc.)
    * Compiler (MSVC, GCC, Clang, Watcom, Turbo C, etc.)
    * CPU architecture (x86, x86_64, ARM, MIPS, etc.)
    * Terminal capabilities (ANSI colors, screen size)

20.2  Platform-Conditional Code

  Modules use platform queries rather than #ifdef:

    if (platform_is_windows()) {
        /* Windows-specific behavior */
    }

  This keeps the code portable without scattering preprocessor
  conditionals throughout every module.

20.3  Line Endings and Paths

  The platform module normalizes:
    * Line endings (CR+LF on Windows, LF on Unix)
    * Path separators (\ on Windows, / on Unix)
    * Console input (kbhit/getch on Windows, termios on Unix)

  BASIC programs do not need to worry about these differences --
  the platform module handles them transparently.

22. DATA FLOW: FROM KEYPRESS TO RESULT
=====================================================================

This section traces the complete path of a BASIC command from
keyboard input to screen output.

EXAMPLE: User types   PRINT 2 + 3

  1. REPL (main.c)
     - fgets() reads "PRINT 2 + 3\n" into input_buf
     - First character is a letter, not a digit -> immediate mode
     - error_clear() resets any previous error

  2. LEXER (lexer.c)
     - lexer_init(&lex, input_buf)
     - lexer_next() produces: TOK_KEYWORD(KW_PRINT)
     - (Parser will call lexer_next() for remaining tokens)

  3. PARSER (parser.c)
     - Sees KW_PRINT -> dispatches to parse_print()
     - parse_print() calls parse_expression()

  4. EXPRESSION EVALUATOR (parser.c)
     - parse_expression() calls parse_additive()
     - parse_additive() calls parse_multiplicative()
     - parse_multiplicative() calls parse_atom()
     - parse_atom() sees TOK_NUMBER(2) -> returns bval_int(2)
     - Back in parse_additive(): sees TOK_PLUS
     - Calls parse_multiplicative() again
     - parse_atom() sees TOK_NUMBER(3) -> returns bval_int(3)
     - parse_additive() adds: 2 + 3 = 5 -> returns bval_int(5)

  5. OUTPUT (parser.c, parse_print)
     - parse_print() receives bval_int(5)
     - Calls bval_to_int() -> 5
     - printf("%ld", 5) -> prints "5" to stdout
     - Prints newline (no trailing semicolon)

  6. RETURN TO REPL (main.c)
     - error_occurred() returns 0 (no error)
     - Print prompt "> "
     - Wait for next input

Total time: microseconds.  No memory allocation occurred (the
number 5 was a stack-local BValue).  No pool memory was consumed.

EXAMPLE: User types   RUN  (with a stored program)

  1. REPL recognizes KW_RUN -> calls exec_run()
  2. exec_run() calls runtime_reset() to clear variables
  3. Loop: for each line in ProgramStore (sorted by line#):
     a. lexer_init() on line text
     b. Skip line number tokens
     c. Parse and execute the statement(s)
     d. Check error_occurred()
     e. Check runtime.next_index for GOTO/GOSUB
     f. Advance to next line (or jump)
  4. On END, STOP, or last line: runtime.running = 0
  5. Return to REPL, print "Ready."

23. EXTENDING BASIC++
=====================================================================

This section provides quick recipes for common extension tasks.

23.1  Adding a New Statement

  1. Add a KeywordId (e.g., KW_MYSTATEMENT) to lexer.h
  2. Add the keyword string to keyword_table[] in lexer.c
  3. Add a parse_mystatement() function in parser.c
  4. Add a case to the statement dispatch switch in parser.c
  5. Test in immediate mode and program mode

23.2  Adding a New Built-In Function

  1. Write the handler in builtins.c:
     BValue builtin_myfunc(RuntimeState *rt, BValue *args, int n)
  2. Register it in funcreg_init() or in a module's init:
     funcreg_register("MYFUNC$", FUNC_STRING, 1, 1,
                      builtin_myfunc, 0)
  3. The parser automatically finds it via registry lookup

23.3  Adding a New Dialect

  1. Add a DialectType enum value in dialect.h
  2. Create a DialectConfig in dialect.c describing the keyword
     set, function set, and behavior flags
  3. Add a case to dialect_init() for the new dialect
  4. Test with DIALECT MYBASIC

23.4  Adding a New Module

  1. Create mod_xxx.h and mod_xxx.c
  2. Implement register, init, and shutdown functions
  3. Register functions and/or devices in the init function
  4. Add mod_xxx_register() to main.c's boot sequence
  5. Add to Makefile

23.5  Adding a New Virtual Device

  1. Write read/write/open/close handler functions
  2. Call vdev_register() with name, class, caps, and handlers
  3. The device is immediately accessible from BASIC via
     OPEN, INP, OUT, and VDEV commands
