1. Why Build for FreeDOS?

FreeDOS runs on real vintage hardware (8086/286/386+ PCs), virtual machines
(DOSBox, QEMU, VirtualBox), and embedded DOS controllers. BASIC++ can run
on all of these with a slim build that fits within the 640K conventional
memory limit (16-bit) or uses extended memory via DOS/4GW (32-bit).

The FreeDOS build strips out features that require a modern OS (dynamic
library loading, JIT, network sockets) and reduces memory pools to fit
within tight RAM constraints. The result is a fully functional BASIC
interpreter in a single bpp.exe file.


2. Prerequisites

You need the OpenWatcom C compiler. It is the only C compiler that
produces real-mode 16-bit DOS executables and DOS/4GW 32-bit executables.

Option A: Build natively on FreeDOS

Install OpenWatcom on FreeDOS itself. Download from:
  https://github.com/open-watcom/open-watcom-v2/releases

Set up the environment:
SET WATCOM=C:\WATCOM
SET PATH=%WATCOM%\BINW;%PATH%
SET INCLUDE=%WATCOM%\H

Option B: Cross-compile from Windows 11

Install OpenWatcom v2 for Windows. The Windows-hosted cross-compiler
produces DOS executables without needing a DOS machine:
SET WATCOM=C:\WATCOM
SET PATH=%WATCOM%\BINNT;%PATH%
SET INCLUDE=%WATCOM%\H

Option C: Cross-compile from Linux

Install OpenWatcom v2 for Linux:
export WATCOM=/opt/watcom
export PATH=$WATCOM/binl64:$PATH
export INCLUDE=$WATCOM/h

On Debian/Ubuntu you can also install via package:
# Download from https://github.com/open-watcom/open-watcom-v2/releases
chmod +x open-watcom-2_0-c-linux-x64
sudo ./open-watcom-2_0-c-linux-x64


3. Quick Build (16-bit Real Mode)

This produces a 16-bit real-mode executable that runs on any DOS system,
including original 8086/8088 hardware:

cd source
make watcom

Or manually:
wcc -ml -0 -bt=dos -za -wx -DBPP_FREEDOS -i=. core\main.c
wcc -ml -0 -bt=dos -za -wx -DBPP_FREEDOS -i=. core\memory.c
... (all source files)
wlink name ..\bpp.exe system dos file *.obj

Compiler flags explained:

  Flag                Purpose
  ----------------------------------------------------------------------
  -ml                 Large memory model (far pointers, > 64K code + data)
  -0                  Generate 8086 code (runs on any x86 CPU)
  -bt=dos             Target DOS platform
  -za                 Strict ANSI C compliance
  -wx                 Maximum warnings
  -DBPP_FREEDOS       Activate the FreeDOS build profile in config.h
  -i=.                Include current directory for headers

The output is bpp.exe in the project root.


4. Quick Build (32-bit Protected Mode with DOS/4GW)

This produces a 32-bit executable that uses the DOS/4GW protected-mode
extender. It can access extended memory beyond 640K, allowing larger
programs and string pools:

cd source
make watcom386

Or manually:
wcc386 -bt=dos -za -wx -DBPP_FREEDOS -i=. core\main.c
wcc386 -bt=dos -za -wx -DBPP_FREEDOS -i=. core\memory.c
... (all source files)
wlink name ..\bpp.exe system dos4g file *.obj

Key differences from 16-bit:

  Feature             16-bit (wcc)        32-bit (wcc386)
  ----------------------------------------------------------------------
  CPU required        8086+               386+
  Memory limit        640K conventional   Extended memory (4 GB theoretical)
  Pointer size        16-bit far (seg:off)32-bit flat
  Extender            None                DOS/4GW (bundled with Watcom)
  Pool sizes          Limited by 640K     Can increase in config.h

When to use 32-bit: If you have a 386 or better and want larger
programs, more string space, or additional dialects.


5. Cross-Compiling from Windows 11

You can build the FreeDOS executable on Windows 11 without ever
booting into DOS:

REM Set up Watcom environment
SET WATCOM=C:\WATCOM
SET PATH=%WATCOM%\BINNT;%PATH%
SET INCLUDE=%WATCOM%\H

REM Navigate to source directory
CD source

REM Build 16-bit DOS executable
make watcom

REM Or build 32-bit DOS/4GW executable
make watcom386

The resulting bpp.exe can be copied to a FreeDOS machine, USB drive,
floppy disk image, or DOSBox directory.

Testing with DOSBox:
REM After building:
copy ..\bpp.exe C:\DOSBox\BASIC\
dosbox -c "mount c c:\dosbox\basic" -c "c:" -c "bpp.exe"


6. Cross-Compiling from Linux

# Set up Watcom environment
export WATCOM=/opt/watcom
export PATH=$WATCOM/binl64:$PATH
export INCLUDE=$WATCOM/h

cd source

# Build 16-bit DOS executable
make watcom

# Or 32-bit DOS/4GW
make watcom386

Testing with DOSBox on Linux:
# After building:
cp ../bpp.exe ~/dosbox/
dosbox -c "mount c ~/dosbox" -c "c:" -c "bpp.exe"

Testing with QEMU:
# Create a FreeDOS boot disk image, copy bpp.exe to it
# Then boot with:
qemu-system-i386 -m 16 -fda freedos.img

  Math                builtins_math.c     Math functions

Adding Excluded Components Back

You CAN add any excluded component back if your system has enough
memory.  See "Customizing Your FreeDOS Build" below.


8. Memory Budget

16-bit Build (640K conventional memory)

Total conventional memory:           640 KB
DOS + drivers (typical):            -100 KB
Available for applications:         ~540 KB

BASIC++ code segment:               -180 KB  (approximate .exe size)
BASIC++ data segment:               -160 KB  (memory pools, see below)
C runtime + stack:                   -20 KB
                                    --------
Remaining free:                     ~180 KB

Pool breakdown (from config.h BPP_FREEDOS section):

  Pool                Size                Purpose
  ----------------------------------------------------------------------
  Program memory      32 KB               Stored BASIC program text
  Variable memory     16 KB               Runtime variables
  Scratch memory      16 KB               Tokenizer/parser workspace
  String pool         32 KB               String values during RUN
  Array pool          ~64 KB              4,096 elements x 16 bytes
  Total pools         ~160 KB

Additional limits:

  Resource            Limit
  ----------------------------------------------------------------------
  Program lines       1,024
  Stack depth         64
  Named variables     128
  DATA items          1,024
  DIM arrays          32
  Array elements      4,096
  User functions      32
  Modules             8
  Breakpoints         16
  User types          8
  Graphics            160 x 100

32-bit Build (Extended memory via DOS/4GW)

With the 32-bit build, you can increase pool sizes in config.h because
DOS/4GW provides access to extended memory:

// Example: larger pools for 32-bit FreeDOS build
#define PROGRAM_MEMORY_SIZE   131072L   // 128 KB
#define MAX_PROGRAM_LINES     4096
#define MAX_STRING_POOL       131072L   // 128 KB
#define MAX_ARRAY_ELEMENTS    16384     // 16K elements
#define MAX_NAMED_VARS        512


9. Customizing Your FreeDOS Build

9.1 Changing the Default Dialect

The FreeDOS build defaults to Palo Alto Tiny BASIC (PATB), the
smallest dialect. To change the default, edit config.h:

// In the BPP_FREEDOS section:
#undef BASICPP_DEFAULT_DIALECT
#define BASICPP_DEFAULT_DIALECT DIALECT_GW_BASIC  // or any other

You must also compile the dialect's source file and register it
in dialect.c (see "Adding Dialects Back" below).

9.2 Adding Dialects Back

Each dialect is a single .c file (~3-15 KB of code). To add GW-BASIC:

Step 1: In dialect.h, ensure the registration function is declared:
void dialect_register_gwbasic(void);

Step 2: In dialect.c, call the registration function in
dialect_init() (remove any #ifndef BPP_FREEDOS guard):
dialect_register_gwbasic();

Step 3: Add the file to the Makefile's WATCOM_SOURCES:
WATCOM_SOURCES += dialect/dialect_gwbs.c

Step 4: Rebuild:
make clean
make watcom

Step 5: Verify:
bpp.exe
> DIALECT "GWBS"
> DIALECT LIST

Memory cost per dialect (approximate):

  Dialect             Code                Code Size
  ----------------------------------------------------------------------
  PATB (Tiny BASIC)   dialect_patb.c      ~3 KB
  TRS-80 Level I      dialect_trs1.c      ~4 KB
  TRS-80 Level II     dialect_trs2.c      ~5 KB
  GW-BASIC            dialect_gwbs.c      ~8 KB
  ECMA-55             dialect_ecma55.c    ~5 KB
  ECMA-116            dialect_ecma116.c   ~10 KB
  QBasic              dialect_qbasic.c    ~12 KB
  Apple Integer       dialect_aint.c      ~4 KB
  AppleSoft           dialect_asft.c      ~6 KB
  Atari BASIC         dialect_atari.c     ~5 KB
  Commodore 64        dialect_c64.c       ~6 KB
  Color Computer      dialect_coco.c      ~5 KB
  MBASIC (CP/M)       dialect_mbasic.c    ~5 KB
  Sinclair BASIC      dialect_sinclair.c  ~5 KB
  SuperBASIC (QL)     dialect_superbasic.c~6 KB
  SUPER BASIC         dialect_sbasic.c    ~8 KB

9.3 Adding Modules Back

To restore a module (e.g., the transpiler):

1. Add its source files to WATCOM_SOURCES in the Makefile
2. Remove any #ifndef BPP_FREEDOS guard in main.c around
   its registration call
3. Rebuild

9.4 Adjusting Memory Pool Sizes

Edit the BPP_FREEDOS section of config.h:

For more program space (larger BASIC programs):
#define PROGRAM_MEMORY_SIZE   65536L    // 64 KB (was 32 KB)
#define MAX_PROGRAM_LINES     2048      // (was 1,024)

For more string space (string-heavy programs):
#define MAX_STRING_POOL       65536L    // 64 KB (was 32 KB)

For tiny systems (256K or less):
#define PROGRAM_MEMORY_SIZE   16384L    // 16 KB
#define MAX_PROGRAM_LINES     512
#define MAX_STRING_POOL       16384L    // 16 KB
#define MAX_ARRAY_ELEMENTS    2048

Always rebuild after editing config.h:
make clean
make watcom


10. Union Mode on FreeDOS

Even though the FreeDOS build only includes one dialect (PATB by
default), BASIC++ still operates in Union Mode. This means:

- All core BASIC keywords work regardless of dialect
- PRINT, INPUT, IF/THEN/ELSE, FOR/NEXT, WHILE/WEND, etc. are always available
- The dialect setting controls prompts, statement separators, and
  feature gates -- not which keywords the parser recognizes
- You can use GW-BASIC-style commands even in Tiny BASIC mode
  when Union Mode is active

To enable strict dialect enforcement:
OPTION STRICT       ' Only allow keywords from the active dialect
OPTION STRICT OFF   ' Return to Union Mode (default)


11. Which BASIC Features Work on FreeDOS

These features work identically on FreeDOS and Windows/Linux:

- REPL (interactive prompt)
- All core statements: PRINT, INPUT, LET, IF/THEN/ELSE, FOR/NEXT,
  WHILE/WEND, DO/LOOP, SELECT CASE, GOTO, GOSUB/RETURN
- DEF FN user-defined functions
- SUB/FUNCTION blocks (QBasic-style, Union Mode)
- String operations: LEFT$, RIGHT$, MID$, LEN, ASC, CHR$, etc.
- Math functions: SIN, COS, TAN, SQR, LOG, EXP, ABS, INT, RND
- File I/O: OPEN, CLOSE, PRINT#, INPUT#, LINE INPUT#, EOF, LOF
- Random-access files: GET#, PUT#, FIELD, LSET, RSET
- Error handling: ON ERROR GOTO, RESUME, ERR, ERL
- PEEK/POKE with MEMMAP virtual memory
- ALIAS keyword remapping
- Security sandboxing
- HELP command
- SELFTEST diagnostics
- TRON/TROFF trace mode
- SAVE/LOAD/LIST/RUN/NEW
- Text-mode graphics (160x100 in FreeDOS, 320x200 on modern)


12. Which BASIC Features Are Excluded

These features require a modern OS and are not available:

- SHELL (no subshell spawning -- DOS COMMAND.COM is not called)
- Dynamic library loading (no DLL/SO support)
- Network I/O (no TCP/IP stack)
- JIT compilation (no executable memory mapping)
- USB device access
- FujiNet / UPnP discovery
- COMPILE (transpiler, excluded to save code size)

15. Troubleshooting

"SORRY. Cannot allocate memory."
The interpreter cannot malloc() enough memory at startup.
- Reduce pool sizes in config.h (see section 9.4)
- Free conventional memory by unloading TSRs and device drivers
- Try the 32-bit build (make watcom386) for extended memory access

"Unknown dialect"
You tried to switch to a dialect that is not compiled in.
On FreeDOS, only PATB is available by default.
- Add the dialect back (see section 9.2)

Linker error: "segment too large"
The 16-bit build exceeds the 64K segment limit.
- You have added too many dialect or module files
- Remove some, or switch to the 32-bit build

"Undefined reference to _mod_usb_register"
You uncommented the USB module registration in main.c but did not
add mod_usb.c to the Makefile.
- Add the .c file to WATCOM_SOURCES, or re-comment the registration

Program runs out of string space
The 32 KB string pool is exhausted during RUN.
- Use shorter strings or fewer string concatenations
- Increase MAX_STRING_POOL in config.h and rebuild

Build fails with "Cannot open include file"
- Make sure -i=. is in your compile flags
- Verify that you are running make from the source/ directory

bpp.exe crashes on DOSBox
- DOSBox default memory may be too low. Edit dosbox.conf:

  [dosbox]
  memsize=16

- Or use DOSBox-X which has better memory management
