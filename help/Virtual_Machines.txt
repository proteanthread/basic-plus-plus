VIRTUAL MACHINES, VIRTUAL CONSOLES, AND VIRTUAL TERMINALS
==========================================================
Version 0.21.0

BASIC++ provides three layers of virtualization that together
emulate complete 8-bit and 16-bit computer environments
entirely in software:

  Virtual Machine   - the execution engine, dispatch table,
                      and state machine that runs BASIC programs

  Virtual Console   - screen buffers, cursor tracking, color
                      registers, and graphics framebuffer

  Virtual Terminal  - ANSI/VT escape code handling, keyboard
                      input abstraction, and terminal type
                      emulation

This guide explains how they work, how to use them, and how
to combine them into fully emulated vintage machines.

=====================================================================
1. OVERVIEW: THE THREE LAYERS
=====================================================================

The virtualization stack has three distinct layers.  Each layer
can be used independently or combined for full machine emulation.

  +------------------------------------------------------+
  |                  BASIC++ Program                      |
  +------------------------------------------------------+
  |  VIRTUAL MACHINE (VM)                                 |
  |  - Opcode dispatch table                              |
  |  - State machine (STOPPED/RUNNING/PAUSED/HALTED)      |
  |  - Expression evaluation stack                        |
  |  - Control flow (GOTO/GOSUB/RETURN/FOR-NEXT)          |
  +------------------------------------------------------+
  |  VIRTUAL CONSOLE                                      |
  |  - Screen buffer (text: 80x25, gfx: 320x200)         |
  |  - Cursor position and shape                          |
  |  - Color attributes (foreground/background)           |
  |  - Multiple pages (SCREEN 0-7)                        |
  |  - Graphics framebuffer (PSET/LINE/CIRCLE)            |
  +------------------------------------------------------+
  |  VIRTUAL TERMINAL                                     |
  |  - ANSI/VT escape code translation                    |
  |  - Character set mapping (ASCII/PETSCII/ATASCII)      |
  |  - Keyboard scan code abstraction                     |
  |  - Terminal capability detection                      |
  +------------------------------------------------------+
   |  VDev LAYER (VDev2 - Phase 16)                       |
   |  - CON: console device                                |
   |  - ERR: error device                                  |
   |  - FILE: file I/O device (with binary R/W/seek)       |
   |  - User-registered devices (slots 3-63)               |
   |  - Device classes, caps, IOCTL2, discovery             |
  +------------------------------------------------------+
  |  HOST OPERATING SYSTEM                                |
  |  - stdout/stdin/stderr (Windows, Linux, FreeDOS)      |
  |  - File system, keyboard, speaker                     |
  +------------------------------------------------------+

Key principle: the interpreter NEVER calls host OS functions
directly.  All I/O flows through VDev function pointers,
which the Virtual Terminal and Virtual Console layers
implement.  This makes the entire stack portable and
interceptable.


=====================================================================
2. THE VIRTUAL MACHINE (VM)
=====================================================================


---------------------------------------------------------------------
2.1  VM Architecture
---------------------------------------------------------------------

The VM is the execution engine of BASIC++.  It replaces the
ad-hoc while-loop that earlier prototype interpreters used
with a formalized, three-component architecture:

  1. STATE MACHINE
     A single enum (VMState) tracks exactly what the VM is
     doing at any moment.  No more checking multiple boolean
     flags scattered across struct fields.

  2. DISPATCH TABLE
     A static table mapping every BASIC keyword to an opcode
     and handler function pointer.  Statement execution is
     O(1) lookup instead of a giant switch statement.

  3. EVALUATION STACK
     A bounded stack for expression evaluation, providing the
     infrastructure for future bytecode compilation while
     remaining compatible with the current recursive evaluator.

This design was introduced in Phase 12 and provides the
foundation for:
  - Phase 13: Bytecode format (.BPP files)
  - Phase 14: Module system (sandboxed dispatch)
  - Phase 15: Security (capability-gated handlers)
  - Phase 16: Cross-platform backends


---------------------------------------------------------------------
2.2  Execution States
---------------------------------------------------------------------

The VM operates in exactly one of five states:

  State        Value  Description
  -----        -----  -----------
  VM_STOPPED   0      Idle at the REPL prompt.  No program
                      is executing.  User can enter commands,
                      edit program lines, or type RUN.

  VM_RUNNING   1      A program is executing.  The VM fetches
                      the next line, resolves its opcode, and
                      calls the handler.  This continues until
                      the state changes.

  VM_PAUSED    2      A STOP statement was encountered.  The
                      program is suspended but can be resumed
                      with CONT.  Variables are preserved.

  VM_ERROR     3      A runtime error occurred.  The error
                      handler has been invoked and an error
                      message displayed.  If ON ERROR GOTO
                      is active, execution continues at the
                      error handler line.

  VM_HALTED    4      An END statement was encountered.  The
                      program has finished normally.  Variables
                      are preserved (they can be PRINTed at
                      the REPL) but the program cannot be
                      CONTinued.

State transitions:

  VM_STOPPED --> VM_RUNNING       RUN command
  VM_RUNNING --> VM_PAUSED        STOP statement
  VM_RUNNING --> VM_HALTED        END statement
  VM_RUNNING --> VM_ERROR         Runtime error
  VM_PAUSED  --> VM_RUNNING       CONT command
  VM_ERROR   --> VM_RUNNING       ON ERROR GOTO handler
  VM_ERROR   --> VM_STOPPED       Unhandled error (back to REPL)
  VM_HALTED  --> VM_STOPPED       User types NEW, RUN, or edits

The key insight is that VM_PAUSED preserves the program
counter and all state, so CONT can seamlessly resume
execution from the line after STOP.


---------------------------------------------------------------------
2.3  The Dispatch Table
---------------------------------------------------------------------

Every BASIC keyword maps to exactly one opcode and one
handler function.  At boot time, vm_init() populates a
static dispatch table with these mappings.

Dispatch table entry structure:

  struct VMDispatchEntry {
      VMOpcode    opcode;     /* OP_PRINT, OP_GOTO, etc.  */
      KeywordId   keyword;    /* KW_PRINT, KW_GOTO, etc.  */
      VMHandler   handler;    /* function pointer          */
      const char *name;       /* "PRINT", "GOTO" (for TRON) */
  };

Handler function signature:

  void handler(Lexer *lex, void *rt, int line_num);

This uniform signature means:
  - The lexer is positioned just after the statement keyword
  - The runtime state provides all program context
  - The line number enables meaningful error messages

The handler is responsible for:
  - Consuming tokens from the lexer (arguments, expressions)
  - Performing its operation (output, variable assignment, etc.)
  - Setting the next line index (for flow control)
  - Signaling errors via the error system

Because the signature matches the existing parse_xxx()
functions exactly, migration from the old switch-based
dispatch to the VM dispatch was zero-cost.

Execution path:

  1. VM fetches the current program line
  2. Lexer tokenizes the line and identifies the first keyword
  3. vm_resolve_opcode() maps KeywordId -> VMOpcode  [O(1)]
  4. vm_get_handler() maps VMOpcode -> function pointer [O(1)]
  5. Handler is called
  6. VM advances to the next line (or follows a jump)


---------------------------------------------------------------------
2.4  Expression Evaluation Stack
---------------------------------------------------------------------

The VM provides a bounded evaluation stack for expressions:

  struct VMEvalStack {
      BValue items[VM_EVAL_STACK_SIZE];  /* 64 slots */
      int    top;   /* -1 = empty */
  };

Operations:
  vm_eval_init(stk)         Clear the stack
  vm_eval_push(stk, val)    Push a value (returns 0 or -1)
  vm_eval_pop(stk)          Pop and return top value
  vm_eval_peek(stk)         Read top value without popping
  vm_eval_depth(stk)        Current number of items

Stack overflow raises ERR_SORRY ("Sorry, I can't do that").
Stack underflow raises ERR_HOW ("How?").

Currently, the recursive descent expression evaluator in
parser.c uses the C call stack directly.  The VMEvalStack
provides the infrastructure for the future bytecode VM
(Phase 13) where expressions will be compiled to stack
operations (PUSH, ADD, MUL, CALL_FN, etc.).

Both systems coexist — the recursive evaluator for
interpreted mode, and the stack for compiled mode.


---------------------------------------------------------------------
2.5  Control Flow Primitives
---------------------------------------------------------------------

All control flow goes through these VM functions:

  vm_jump(rt, target_line, line_num)
    Unconditional jump to a target line number.
    Resolves line number to program store index.
    Raises ERR_HOW if the line doesn't exist.
    Used by: GOTO, computed GOTO, ON...GOTO

  vm_call(rt, target_line, line_num)
    Subroutine call.  Pushes a GOSUB frame with the
    return address, then jumps to the target line.
    Raises ERR_SORRY if the stack is full.
    Used by: GOSUB, ON...GOSUB

  vm_return_sub(rt, line_num)
    Return from subroutine.  Pops the top GOSUB frame
    and jumps to the return address.
    Raises ERR_HOW if the stack is empty or the frame
    is not a GOSUB frame.
    Used by: RETURN

  vm_halt(rt)
    Halt execution.  Sets state to VM_HALTED.
    Used by: END

  vm_stop(rt)
    Pause execution.  Sets state to VM_PAUSED.
    Used by: STOP

These primitives encapsulate all the line-number-to-index
resolution and stack operations that were previously
scattered across parser.c and exec.c.


---------------------------------------------------------------------
2.6  The Execution Loop
---------------------------------------------------------------------

The main execution loop is straightforward:

  1. Check state == VM_RUNNING, else exit loop
  2. Fetch program line at current index
  3. If TRON is active, print the line number
  4. Check for breakpoints (if debugger active)
  5. Tokenize the line via the lexer
  6. Identify the first token (keyword or variable name)
  7. If keyword: vm_dispatch(keyword_id, lex, rt, line_num)
  8. If variable: implicit LET assignment
  9. Advance to next line (unless handler already set it)
  10. Repeat from step 1

The loop processes one BASIC line per iteration.  Multi-
statement lines (separated by ':') are handled within
the handler — the loop itself processes one logical line.

Timing:
  - On modern hardware, the loop processes millions of
    BASIC lines per second.
  - No artificial speed throttling is applied by default.
  - Use DELAY or a timing loop for paced execution.


---------------------------------------------------------------------
2.7  VM Boot Sequence
---------------------------------------------------------------------

When basicpp.exe starts, the following initialization
sequence executes:

  Step 1: platform_init()     Detect OS and compiler
  Step 2: vdev_init()         Create CON:/ERR:/FILE: devices
  Step 3: vm_init()           Populate dispatch table
  Step 4: memmap_init(NONE)   Initialize 64K memory (bare)
  Step 5: runtime_init()      Create runtime state
  Step 6: REPL loop           Begin accepting user input

After boot, the VM is in VM_STOPPED state.  The user is
at the REPL prompt and can type immediate commands, enter
program lines, or type RUN to begin execution.

Commands that work in VM_STOPPED state:
  NEW, LIST, RUN, LOAD, SAVE, MEMMAP, DIALECT, SYSTEM,
  HELP, VER, CATALOG, SELFTEST

Commands that require VM_RUNNING state:
  CONT (resumes from VM_PAUSED only)

All other statements work in both states (direct mode and
program mode).


=====================================================================
3. THE VIRTUAL CONSOLE
=====================================================================


---------------------------------------------------------------------
3.1  Console Architecture
---------------------------------------------------------------------

The Virtual Console provides a platform-independent screen
abstraction.  Regardless of whether BASIC++ is running on
Windows 11, Linux, or FreeDOS, the console presents a
consistent interface:

  - Text mode: 80 columns x 25 rows (or configurable via WIDTH)
  - Graphics mode: 320 x 200 pixels, 16 colors
  - Cursor tracking: row, column, visibility, shape
  - Color registers: 16 foreground + 16 background colors
  - Multiple screen pages: 0 through 7
  - Input buffer: type-ahead with INKEY$ support

The console does NOT directly call printf or putchar.
All output goes through the CON: virtual device, which
translates console operations into host-appropriate
sequences (ANSI escapes on Linux, Win32 Console API on
Windows, direct INT 10h on FreeDOS).


---------------------------------------------------------------------
3.2  Screen Buffers
---------------------------------------------------------------------

The console maintains a virtual screen buffer — a 2D array
of character cells.  Each cell contains:

  - Character code (0-255)
  - Foreground color (0-15)
  - Background color (0-15)
  - Attribute flags (blink, bold, underline, reverse)

This buffer is the source of truth for the screen contents.
When a PRINT statement writes text, the characters go into
the buffer first, then the buffer is rendered to the host
terminal.

Screen buffer dimensions:

  Mode          Columns  Rows  Cells   Memory
  ----          -------  ----  -----   ------
  80x25 text    80       25    2000    4000 bytes
  80x50 text    80       50    4000    8000 bytes
  40x25 text    40       25    1000    2000 bytes
  132x44 text   132      44    5808    11616 bytes

Each cell uses 2 bytes (character + attribute), matching
the layout of IBM PC video memory.

Setting the screen mode:

  WIDTH 80                 80-column mode (default)
  WIDTH 40                 40-column mode
  WIDTH 132                132-column mode (if terminal supports)
  SCREEN 0                 Text mode
  SCREEN 1                 320x200 graphics mode
  SCREEN 2                 640x200 graphics mode


---------------------------------------------------------------------
3.3  Cursor Management
---------------------------------------------------------------------

The virtual console tracks cursor position independently
of the host terminal cursor.  This provides consistent
behavior across platforms.

Cursor state:
  - Row (1-based, 1 = top row)
  - Column (1-based, 1 = left column)
  - Visible (on/off)
  - Shape (block, underline, line)

Cursor commands:

  LOCATE row, col          Move cursor to position
  LOCATE row               Move cursor to row, keep column
  LOCATE , col             Keep row, move cursor to column
  LOCATE ,,1               Show cursor
  LOCATE ,,0               Hide cursor

  POS(0)                   Return current cursor column
  CSRLIN                   Return current cursor row

  PRINT TAB(n)             Move to column n
  PRINT SPC(n)             Print n spaces

Cursor behavior:
  - Printing past column 80 wraps to the next row
  - Printing past row 25 scrolls the screen up
  - A semicolon (;) at the end of PRINT suppresses newline
  - A comma (,) advances to the next 14-character print zone

Example:
  LOCATE 12, 40            ' Move to center of screen
  COLOR 14, 1              ' Yellow on blue
  PRINT "HELLO";           ' Print without newline
  PRINT " WORLD"           ' Print on same line


---------------------------------------------------------------------
3.4  Color System
---------------------------------------------------------------------

The console supports 16 foreground and 16 background colors,
matching the IBM CGA/EGA/VGA text-mode palette:

  Code  Color           Code  Color
  ----  -----           ----  -----
   0    Black             8    Dark Gray
   1    Blue              9    Light Blue
   2    Green            10    Light Green
   3    Cyan             11    Light Cyan
   4    Red              12    Light Red
   5    Magenta          13    Light Magenta
   6    Brown/Dark Yel   14    Yellow
   7    White/Light Gray 15    Bright White

Setting colors:

  COLOR foreground               Set text color
  COLOR foreground, background   Set text and background
  COLOR , background             Keep text, set background

Examples:
  COLOR 15, 1                    ' Bright white on blue
  CLS                            ' Clear screen with current bg
  COLOR 14                       ' Yellow text
  PRINT "WARNING!"

The graphics framebuffer supports the same 16 colors for
PSET, LINE, CIRCLE, and PAINT operations.

PALETTE command (remap colors):

  PALETTE attr, color            Remap attribute to new color
  PALETTE 0, 1                   ' Remap "black" to blue
  PALETTE                        ' Reset all colors to defaults

On platforms with ANSI color support (most modern terminals),
colors are rendered using SGR escape sequences.  On FreeDOS,
the BIOS INT 10h functions are used directly.


---------------------------------------------------------------------
3.5  Multiple Console Pages
---------------------------------------------------------------------

The console supports up to 8 screen pages (0-7).  Each page
has its own independent screen buffer, cursor position, and
color state.

  SCREEN , , apage, vpage
    apage = active page (where PRINT writes)
    vpage = visual page (which page is displayed)

Page operations:

  SCREEN , , 0, 0          ' Write to page 0, display page 0
  SCREEN , , 1, 0          ' Write to page 1, display page 0
  SCREEN , , 1, 1          ' Write to page 1, display page 1

This enables double-buffering:

  ' Set up double buffering
  VISUAL = 0 : ACTIVE = 1
  DO
    SCREEN , , ACTIVE, VISUAL    ' Draw on hidden page
    CLS
    LOCATE 10, 30
    PRINT "Frame "; FRAME
    FRAME = FRAME + 1
    ' Swap pages
    SWAP VISUAL, ACTIVE
  LOOP

Note: On text-mode terminals, page switching is emulated
by storing multiple buffers and re-rendering.  The effect
is instantaneous on modern hardware.

PCOPY command (copy between pages):

  PCOPY source, dest       ' Copy page contents
  PCOPY 0, 1               ' Copy page 0 to page 1


---------------------------------------------------------------------
3.6  Screen Modes (TEXT vs GRAPHICS)
---------------------------------------------------------------------

BASIC++ supports two primary display modes:

TEXT MODE (SCREEN 0):
  - Default mode at startup
  - Character-based display (80x25 or 40x25)
  - CLS, LOCATE, COLOR, PRINT, INPUT operate normally
  - Scrolling when text reaches the bottom

GRAPHICS MODE (SCREEN 1 / SCREEN 2):
  - Pixel-based display using the graphics framebuffer
  - SCREEN 1: 320x200, 4 colors per pixel
  - SCREEN 2: 640x200, 2 colors per pixel
  - PSET, LINE, CIRCLE, PAINT, DRAW, POINT are active
  - Text can still be printed (overlaid on graphics)
  - CLS clears the entire framebuffer

Switching modes:

  SCREEN 0                 ' Switch to text mode
  SCREEN 1                 ' Switch to 320x200 graphics
  SCREEN 2                 ' Switch to 640x200 graphics

Mode detection:

  IF SCREEN = 0 THEN PRINT "Text mode"
  IF SCREEN > 0 THEN PRINT "Graphics mode"


---------------------------------------------------------------------
3.7  The Graphics Framebuffer
---------------------------------------------------------------------

The graphics framebuffer (gfxbuf) is a virtual pixel buffer
that renders to the terminal using ANSI escape codes and
Unicode half-block characters.

Resolution: 320 x 200 pixels (configurable in config.h)
Colors: 16 (CGA/EGA palette, remappable via PALETTE)
Rendering: Unicode half-block characters (U+2580 upper,
           U+2584 lower) give 2 vertical pixels per
           terminal character cell.
Terminal grid: 80 columns x 100 rows for 320x200 resolution.

Graphics commands:

  PSET (x, y), color       ' Set a pixel
  PRESET (x, y)            ' Reset pixel to background
  LINE (x1,y1)-(x2,y2), c ' Draw a line
  LINE (x1,y1)-(x2,y2),,B ' Draw a rectangle outline
  LINE (x1,y1)-(x2,y2),,BF' Draw a filled rectangle
  CIRCLE (cx,cy), r, c     ' Draw a circle
  PAINT (x, y), fill, bord ' Flood fill area
  POINT(x, y)              ' Read pixel color
  DRAW command$             ' Turtle graphics

Drawing algorithms:
  - LINE uses Bresenham's line algorithm
  - CIRCLE uses the midpoint circle algorithm
  - PAINT uses recursive flood fill

Example — drawing a starfield:

  SCREEN 1
  CLS
  FOR I = 1 TO 200
    X = INT(RND * 320)
    Y = INT(RND * 200)
    C = INT(RND * 15) + 1
    PSET (X, Y), C
  NEXT
  LOCATE 1, 1
  COLOR 15
  PRINT "Press any key..."
  A$ = INPUT$(1)
  SCREEN 0


---------------------------------------------------------------------
3.8  Console Commands
---------------------------------------------------------------------

Complete list of console-related commands:

  DISPLAY:
    CLS                    Clear screen (current page)
    COLOR fg, bg           Set text colors
    LOCATE row, col        Position cursor
    WIDTH n                Set screen width (40/80/132)
    SCREEN mode            Set screen mode (0/1/2)
    PCOPY src, dst         Copy screen page
    PALETTE attr, color    Remap color

  CURSOR:
    LOCATE r, c, vis       Position + visibility
    POS(0)                 Current column
    CSRLIN                 Current row
    PRINT TAB(n)           Tab to column
    PRINT SPC(n)           Skip n spaces

  GRAPHICS:
    PSET (x,y), c          Plot pixel
    PRESET (x,y)           Clear pixel
    LINE coords, c, style  Draw line/box
    CIRCLE (x,y), r, c     Draw circle
    PAINT (x,y), f, b      Flood fill
    DRAW cmd$              Turtle graphics
    POINT(x,y)             Read pixel
    WINDOW (x1,y1)-(x2,y2) Set logical coordinates
    VIEW (x1,y1)-(x2,y2)   Set viewport

  OUTPUT:
    PRINT expression       Print to screen
    PRINT USING fmt; args  Formatted print

  INPUT:

    INKEY$                 Non-blocking key check
    INPUT$(n)              Read n characters


=====================================================================
4. THE VIRTUAL TERMINAL
=====================================================================


---------------------------------------------------------------------
4.1  Terminal Architecture
---------------------------------------------------------------------

The Virtual Terminal sits between the Virtual Console and
the host operating system.  Its job is translation:

  Console operations       Terminal sequences
  ------------------       ------------------
  LOCATE 5, 10      -->    ESC[5;10H
  COLOR 14, 1       -->    ESC[1;33;44m
  CLS               -->    ESC[2J ESC[H
  cursor hide        -->    ESC[?25l
  cursor show        -->    ESC[?25h

The terminal layer automatically detects the host's
terminal capabilities and chooses the appropriate
escape sequences:

  Platform        Terminal Type    Method
  --------        -------------    ------
  Windows 10+     Windows Console  Win32 Console API
  Windows (old)   CMD.EXE          ANSI.SYS if loaded
  Linux           xterm/VT100      ANSI escape codes
  macOS           Terminal.app     ANSI escape codes
  FreeDOS         ANSI.SYS         ANSI escape codes
  SSH session     remote terminal  ANSI escape codes

For SSH and remote sessions, the terminal type is detected
from the TERM environment variable.


---------------------------------------------------------------------
4.2  ANSI Escape Code Support
---------------------------------------------------------------------

BASIC++ generates standard ANSI/VT100 escape sequences
for all console operations.  The sequences follow the
ECMA-48 / ISO 6429 standard.

These sequences are generated automatically — you do not
need to use them directly.  However, you CAN send raw
escape sequences via CHR$(27) if needed:

  ' Manual ANSI: move cursor to row 5, col 10
  PRINT CHR$(27); "[5;10H";

  ' Manual ANSI: set color to bright yellow on blue
  PRINT CHR$(27); "[1;33;44m";

  ' Manual ANSI: clear screen
  PRINT CHR$(27); "[2J"; CHR$(27); "[H";

BASIC++ recognizes and generates these escape categories:

  CSI = CHR$(27) + "["     Control Sequence Introducer

  Category           Sequence          Description
  --------           --------          -----------
  Cursor movement    CSI n A           Move up n rows
                     CSI n B           Move down n rows
                     CSI n C           Move right n cols
                     CSI n D           Move left n cols
                     CSI r ; c H       Move to row r, col c
                     CSI s             Save cursor position
                     CSI u             Restore cursor position

  Erasing            CSI 2 J           Clear entire screen
                     CSI 0 J           Clear from cursor down
                     CSI 1 J           Clear from cursor up
                     CSI 2 K           Clear entire line
                     CSI 0 K           Clear from cursor to EOL
                     CSI 1 K           Clear from start to cursor

  Colors (SGR)       CSI 0 m           Reset all attributes
                     CSI 1 m           Bold / bright
                     CSI 4 m           Underline
                     CSI 5 m           Blink
                     CSI 7 m           Reverse video
                     CSI 30-37 m       Foreground color
                     CSI 40-47 m       Background color
                     CSI 90-97 m       Bright foreground
                     CSI 100-107 m     Bright background

  Cursor visibility  CSI ? 25 h        Show cursor
                     CSI ? 25 l        Hide cursor

  Scrolling          CSI r ; b r       Set scroll region
                     CSI S             Scroll up
                     CSI T             Scroll down

  Screen modes       CSI ? 1049 h      Alt screen buffer (enter)
                     CSI ? 1049 l      Alt screen buffer (leave)


---------------------------------------------------------------------
4.3  Terminal Types and Emulation
---------------------------------------------------------------------

BASIC++ can emulate several classic terminal types for
authentic retro computing experiences:

  TERM "VT100"          DEC VT100 (default)
    - 80x24 display
    - ANSI escape codes
    - Standard keyboard mapping

  TERM "VT52"           DEC VT52 (legacy)
    - ESC Y r c for cursor positioning
    - ESC H for home
    - ESC J for clear to end of screen
    - Simpler escape set (pre-ANSI)

  TERM "ADM3A"          Lear Siegler ADM-3A
    - ESC = r c for cursor positioning
    - Ctrl-Z for clear screen
    - The terminal CP/M programs expect

  TERM "ANSI"           ANSI.SYS (MS-DOS)
    - Full ANSI X3.64 support
    - Used by DOS BBS door games
    - ANSI art compatible

  TERM "PETSCII"        Commodore PETSCII
    - CHR$(147) for clear screen
    - CHR$(19) for home
    - Commodore color codes (CHR$(144)-CHR$(159))
    - Requires MEMMAP "C64" for full authenticity

  TERM "ATASCII"        Atari ATASCII
    - CHR$(125) for clear screen
    - CHR$(28) for cursor up
    - Atari-specific control codes
    - Requires MEMMAP "ATARI8"

  TERM "NONE"           Raw mode
    - No escape code translation
    - Characters passed through as-is
    - Useful for binary protocols

When a terminal type is selected, the console commands
(CLS, LOCATE, COLOR) emit the correct escape sequences
for that terminal type automatically.


---------------------------------------------------------------------
4.4  Keyboard Abstraction
---------------------------------------------------------------------

The Virtual Terminal provides a unified keyboard interface
regardless of the host platform.

INKEY$ behavior:
  - Non-blocking: returns "" if no key is pressed
  - Single character for printable keys
  - Two-character sequence for special keys:
      CHR$(0) + scan code     (function keys, arrows)

  Key              INKEY$ returns
  ---              -------------
  A                "A"
  Enter            CHR$(13)
  Escape           CHR$(27)
  Backspace        CHR$(8)
  Tab              CHR$(9)
  Up arrow         CHR$(0) + CHR$(72)
  Down arrow       CHR$(0) + CHR$(80)
  Left arrow       CHR$(0) + CHR$(75)
  Right arrow      CHR$(0) + CHR$(77)
  F1               CHR$(0) + CHR$(59)
  F2               CHR$(0) + CHR$(60)
  F3               CHR$(0) + CHR$(61)
  F10              CHR$(0) + CHR$(68)
  Home             CHR$(0) + CHR$(71)
  End              CHR$(0) + CHR$(79)
  Page Up          CHR$(0) + CHR$(73)
  Page Down        CHR$(0) + CHR$(81)
  Insert           CHR$(0) + CHR$(82)
  Delete           CHR$(0) + CHR$(83)

This matches the GW-BASIC/QBasic INKEY$ scan code
convention, ensuring compatibility with classic programs.

On Linux/macOS, ANSI escape sequences from the terminal
are translated to the scan code format above.  On Windows,
the Win32 Console API provides scan codes directly.  On
FreeDOS, BIOS INT 16h is used.


---------------------------------------------------------------------
4.5  Character Sets and Code Pages
---------------------------------------------------------------------

BASIC++ supports multiple character encodings for faithful
platform emulation:

  Code Page   Description              Used By
  ---------   -----------              -------
  CP437       IBM PC (DOS default)     MSDOS, GW-BASIC
  CP850       IBM PC (multilingual)    MS-DOS international
  PETSCII     Commodore (shifted)      C64, C128, VIC-20, PET
  ATASCII     Atari (ATASCII)          Atari 400/800/XL/XE
  ASCII       Standard 7-bit ASCII     Apple II, TRS-80

Character set selection:

  CHRS "CP437"            ' IBM PC code page 437
  CHRS "PETSCII"          ' Commodore PETSCII
  CHRS "ATASCII"          ' Atari ATASCII
  CHRS "ASCII"            ' Standard ASCII

When a non-ASCII character set is active, CHR$() and ASC()
use the selected encoding.  For example:

  CHRS "PETSCII"
  PRINT CHR$(147)          ' Clear screen (PETSCII)
  PRINT CHR$(5)            ' White text (PETSCII)

  CHRS "CP437"
  PRINT CHR$(219)          ' Full block character
  PRINT CHR$(176)          ' Light shade
  PRINT CHR$(177)          ' Medium shade
  PRINT CHR$(178)          ' Dark shade

On modern Unicode terminals, PETSCII and ATASCII characters
are rendered using the closest Unicode equivalents.  Block
graphics, line-drawing characters, and special symbols are
mapped to Unicode block elements.


---------------------------------------------------------------------
4.6  Terminal Capabilities
---------------------------------------------------------------------

The interpreter queries terminal capabilities at startup
and adapts its output accordingly.

Capability detection:

  SYSTEM "TERM"            ' Print terminal info

Output example:
  Terminal type: VT100
  Columns: 80
  Rows: 25
  Colors: 256
  Unicode: Yes
  Mouse: No

Capabilities affect behavior:

  Capability    If Yes              If No
  ----------    ------              -----
  Colors        Full 16-color       Monochrome (bold only)
  Unicode       Half-block graphics ASCII art fallback
  Mouse         MOUSE ON/OFF works  MOUSE commands ignored
  Alt screen    CLS uses alt buffer CLS overwrites scrollback
  256-color     PALETTE extended    16-color CGA palette

On terminals without color support, COLOR commands are
silently ignored and all text appears in the terminal's
default foreground/background.

On terminals without Unicode support, the graphics
framebuffer uses ASCII approximation:

  Unicode half-block      ASCII fallback
  ------------------      --------------
  U+2580 (upper half)     ^ or #
  U+2584 (lower half)     _ or #
  U+2588 (full block)     #
  U+2591 (light shade)    .
  U+2592 (medium shade)   :
  U+2593 (dark shade)     #


=====================================================================
5. MACHINE PRESETS (MEMMAP + DIALECT + CONSOLE)
=====================================================================


---------------------------------------------------------------------
5.1  How Presets Work
---------------------------------------------------------------------

A "virtual machine" in BASIC++ is the combination of three
independent settings that together emulate a specific
vintage computer:

  MEMMAP    Controls the 64K memory layout (ROM signatures,
            hardware registers, screen memory, I/O ports)

  DIALECT   Controls the BASIC syntax and keyword set
            (which commands are available, naming conventions,
            default behaviors)

  TERM      Controls the terminal emulation and character
            set (escape codes, screen dimensions, encoding)

You can set them individually:

  MEMMAP "C64"
  DIALECT "C64"
  TERM "PETSCII"

Or use the MACHINE command to set all three at once:

  MACHINE "C64"            ' Sets MEMMAP, DIALECT, and TERM

The MACHINE command is syntactic sugar for the three
separate commands.  It provides the most authentic
emulation experience with a single statement.


---------------------------------------------------------------------
5.2  Available Machine Presets
---------------------------------------------------------------------

  MACHINE Code    MEMMAP     DIALECT    TERM        Description
  ------------    ------     -------    ----        -----------
  "PC"            MSDOS      GWBS       ANSI        IBM PC / GW-BASIC
  "QBASIC"        MSDOS      QBAS       ANSI        Microsoft QBasic
  "C64"           C64        C64        PETSCII     Commodore 64
  "C128"          C128       C128       PETSCII     Commodore 128
  "VIC20"         VIC20      C64        PETSCII     Commodore VIC-20
  "PLUS4"         PLUS4      C64        PETSCII     Commodore Plus/4
  "PET"           PET        C64        PETSCII     Commodore PET
  "APPLE2"        APPLE2     APPLE      ASCII       Apple II
  "ATARI"         ATARI8     ATARI      ATASCII     Atari 800/XL/XE
  "TRS80"         TRS80      TRS        ASCII       TRS-80 Model I/III
  "SPECTRUM"      SPECTRUM   SPEC       ANSI        ZX Spectrum 48K
  "BPP"           NONE       BPP        VT100       BASIC++ (default)

Example — full Commodore 64 session:

  MACHINE "C64"
  Ready.
  > PRINT PEEK(53280)
   14
  > POKE 53280, 0
  > PRINT CHR$(147)
  (screen clears - PETSCII clear screen)
  > 10 PRINT "HELLO FROM C64"
  > 20 PRINT PEEK(53280)
  > RUN
  HELLO FROM C64
   0


---------------------------------------------------------------------
5.3  Creating a Custom Machine Preset
---------------------------------------------------------------------

You can define your own machine preset from BASIC:

  ' Define a custom "MYCOMPUTER" machine
  MEMMAP "NONE"
  DIALECT "BPP"
  TERM "VT100"
  WIDTH 40

  ' Pre-fill memory with custom hardware layout
  POKE &HFF00, &H42       ' Custom hardware register
  POKE &HFF01, &H07       ' Version number
  FOR I = &H0400 TO &H07E7
    POKE I, ASC(" ")       ' Clear screen memory
  NEXT

  ' Set custom colors
  COLOR 10, 0              ' Green on black (terminal look)

  ' Now run programs in your custom environment
  10 PRINT "WELCOME TO MYCOMPUTER"
  20 PRINT "FREE MEMORY: "; 65536 - 2048
  30 PRINT "VERSION: "; PEEK(&HFF01)
  RUN

For a reusable preset, save the initialization as a
BASIC program:

  ' MYSETUP.BAS - Load before your main program
  10 MEMMAP "NONE"
  20 DIALECT "BPP"
  30 TERM "VT100"
  40 WIDTH 40
  50 COLOR 10, 0
  60 CLS
  70 ' ... custom POKE setup ...
  80 END

Then:
  LOAD "MYSETUP.BAS"
  RUN
  NEW
  LOAD "MYPROGRAM.BAS"
  RUN


=====================================================================
6. THE VDEV LAYER (CONNECTING IT ALL)
=====================================================================


---------------------------------------------------------------------
6.1  Device Routing Architecture
---------------------------------------------------------------------

The VDev (Virtual Device) layer is the lowest abstraction —
it sits between the Virtual Terminal and the host OS.  Every
byte of I/O passes through a VDev.

Device table:

  Slot  Name    Purpose
  ----  ----    -------
  0     CON:    Console (stdout + stdin via terminal layer)
  1     ERR:    Error output (stderr)
  2     FILE:   File I/O channels (#1-#8)
  3-15  (user)  Available for custom devices

Each VDev has function pointers for 8 operations:

  putc(dev, ch)           Write one character
  puts(dev, str)          Write a string
  flush(dev)              Flush buffers
  cls(dev)                Clear/reset device
  getc(dev)               Read one character
  gets(dev, buf, max)     Read a line
  open(dev, path, mode)   Open a resource
  close(dev)              Close the device

Plus convenience functions that don't go through VDev:
  vdev_beep()             Platform-specific audible beep
  vdev_sound(freq, dur)   Tone generation
  vdev_sleep(ms)          Millisecond delay
  vdev_inkey()            Non-blocking keyboard read

See R_Virtual_Devices.txt for full details on creating
custom VDev implementations.


---------------------------------------------------------------------
6.2  I/O Flow Diagram
---------------------------------------------------------------------

Here is the complete path of a PRINT statement:

  PRINT "Hello"
    |
    v
  VM dispatches OP_PRINT handler (parser.c)
    |
    v
  Handler evaluates expression -> "Hello"
    |
    v
  Handler calls vdev_puts(CON, "Hello")
    |
    v
  CON: device dev_puts function pointer
    |
    v
  Virtual Terminal translates to output
    |
    v
  (ANSI escape: set colors, position cursor, write text)
    |
    v
  Virtual Console updates screen buffer
    |
    v
  Host OS: fputs(stdout) or WriteConsole()

And an INPUT statement:

  INPUT "Name? "; N$
    |
    v
  VM dispatches OP_INPUT handler
    |
    v
  Handler calls vdev_puts(CON, "Name? ")    (prompt)
    |
    v
  Handler calls vdev_gets(CON, buf, 255)    (read line)
    |
    v
  CON: device dev_gets function pointer
    |
    v
  Virtual Terminal: read keystrokes, echo, handle editing
    |
    v
  Host OS: fgets(stdin) or ReadConsole()
    |
    v
  Handler stores result in N$ variable


---------------------------------------------------------------------
6.3  Intercepting Output
---------------------------------------------------------------------

Because all output flows through VDev function pointers,
you can intercept it at the C level:

  /* Save the original CON: putc */
  VDev *con = vdev_get(VDEV_CON);
  int (*orig_putc)(VDev*, int) = con->dev_putc;

  /* Install interceptor */
  static int my_putc(VDev *d, int ch) {
      /* Log to file */
      FILE *log = fopen("output.log", "a");
      if (log) { fputc(ch, log); fclose(log); }
      /* Call original */
      return orig_putc(d, ch);
  }
  con->dev_putc = my_putc;

This is used internally for:
  - TRON output (prefixing line numbers)
  - Test harness (capturing output for verification)
  - PRINT > file redirection (not yet implemented)


---------------------------------------------------------------------
6.4  Redirecting Input
---------------------------------------------------------------------

Input can be redirected by replacing CON:'s getc/gets:

  /* Feed input from a script file */
  static FILE *script = NULL;

  static int script_getc(VDev *d) {
      (void)d;
      if (!script) return -1;
      int ch = fgetc(script);
      if (ch == EOF) { fclose(script); script = NULL; return -1; }
      return ch;
  }

  script = fopen("commands.txt", "r");
  con->dev_getc = script_getc;

This enables:
  - Automated testing (feed known inputs, verify outputs)
  - Batch mode execution (basicpp.exe < script.bas)
  - Demo playback (pre-recorded sessions)


=====================================================================
7. MULTI-CONSOLE WORKFLOWS
=====================================================================


---------------------------------------------------------------------
7.1  Page Flipping
---------------------------------------------------------------------

Use multiple screen pages for smooth animation:

  ' Double-buffered animation
  APAGE = 1 : VPAGE = 0
  FOR FRAME = 1 TO 100
    SCREEN , , APAGE, VPAGE    ' Draw on hidden page
    CLS
    X = 160 + INT(100 * SIN(FRAME / 10))
    Y = 100 + INT(50 * COS(FRAME / 10))
    LOCATE Y / 8, X / 4
    PRINT "@"
    ' Swap
    SWAP APAGE, VPAGE
  NEXT

The visual page shows the completed frame while the
active page is being drawn, eliminating flicker.


---------------------------------------------------------------------
7.2  Split Screen
---------------------------------------------------------------------

Use VIEW PRINT to divide the screen into regions:

  ' Top half: program output
  VIEW PRINT 1 TO 12
  CLS
  PRINT "=== OUTPUT ==="

  ' Bottom half: status bar
  VIEW PRINT 14 TO 25
  CLS
  PRINT "=== STATUS ==="

  ' Restore full screen
  VIEW PRINT 1 TO 25

Each region scrolls independently — text in the top
region won't scroll into the bottom region.


---------------------------------------------------------------------
7.3  Debug Console
---------------------------------------------------------------------

Use a separate screen page as a debug console:

  10 SCREEN , , 0, 0          ' Main output on page 0
  20 FOR I = 1 TO 100
  30   PRINT "Processing item "; I
  40   ' Write debug info to page 1
  50   SCREEN , , 1, 0        ' Switch to page 1 (still viewing 0)
  60   LOCATE 1, 1
  70   PRINT "DEBUG: I="; I; " MEM="; FRE(0)
  80   SCREEN , , 0, 0        ' Back to main page
  90 NEXT

Press a key to toggle between views:

  100 K$ = INKEY$
  110 IF K$ = CHR$(9) THEN     ' Tab key
  120   IF VIEWING = 0 THEN
  130     SCREEN , , 0, 1 : VIEWING = 1  ' Show debug page
  140   ELSE
  150     SCREEN , , 0, 0 : VIEWING = 0  ' Show main page
  160   END IF
  170 END IF


---------------------------------------------------------------------
7.4  Dual-Monitor Emulation
---------------------------------------------------------------------

Some vintage machines had dual displays (e.g., C128 with
40-column VIC-II + 80-column VDC).  Emulate this with
two screen pages at different widths:

  ' Page 0: 40-column VIC-II output
  SCREEN , , 0, 0
  WIDTH 40
  COLOR 14, 6               ' Light blue on blue (C64 colors)
  CLS
  PRINT "*** COMMODORE 64 BASIC V2 ***"

  ' Page 1: 80-column VDC output
  SCREEN , , 1, 0            ' Write to page 1, view page 0
  WIDTH 80
  COLOR 10, 0                ' Green on black
  CLS
  PRINT "COMMODORE 128 - 80 COLUMN DISPLAY"

  ' Toggle between monitors with F1
  DO
    K$ = INKEY$
    IF K$ = CHR$(0) + CHR$(59) THEN  ' F1
      IF MONITOR = 0 THEN
        SCREEN , , 0, 1 : MONITOR = 1
      ELSE
        SCREEN , , 0, 0 : MONITOR = 0
      END IF
    END IF
  LOOP

---------------------------------------------------------------------
8.2  Handler Registration
---------------------------------------------------------------------

Handlers are registered during vm_init():

  vm_register(OP_PRINT, KW_PRINT, parse_print, "PRINT");
  vm_register(OP_GOTO,  KW_GOTO,  parse_goto,  "GOTO");
  ...

The handler function signature is uniform:

  void parse_print(Lexer *lex, void *rt, int line_num);

Each handler:
  1. Receives the lexer positioned AFTER the keyword
  2. Parses its arguments from the lexer
  3. Executes the operation
  4. May modify the runtime state (variables, flow, etc.)


---------------------------------------------------------------------
8.3  Trace Mode (TRON/TROFF)
---------------------------------------------------------------------

When TRON (Trace ON) is active, the VM prints the line
number in brackets before executing each line:

  > TRON
  > RUN
  [10] [20] [30] [40] [50]
  Hello World
  [60]

  > TROFF

Trace output goes through vdev_printf(CON, "[%d] ", linenum)
before each handler call.  This means trace output can be
intercepted and redirected like any other output.

Trace works in both interpreted mode and when running from
loaded programs.  It does NOT affect the program's own
output — trace markers are interspersed with program output.


---------------------------------------------------------------------
8.4  State Machine Transitions
---------------------------------------------------------------------

  Event                   From         To            Action
  -----                   ----         --            ------
  RUN command             VM_STOPPED   VM_RUNNING    Begin execution
  END statement           VM_RUNNING   VM_HALTED     Stop execution
  STOP statement          VM_RUNNING   VM_PAUSED     Suspend
  CONT command            VM_PAUSED    VM_RUNNING    Resume
  Runtime error           VM_RUNNING   VM_ERROR      Error handler
  ON ERROR GOTO handler   VM_ERROR     VM_RUNNING    Resume at handler
  Unhandled error         VM_ERROR     VM_STOPPED    Back to REPL
  NEW command             VM_HALTED    VM_STOPPED    Clear program
  User edits line         VM_HALTED    VM_STOPPED    Back to REPL
  Ctrl+C / BREAK          VM_RUNNING   VM_STOPPED    Abort

11. LIMITATIONS AND CONSTRAINTS
=====================================================================

  VIRTUAL MACHINE:
  - Maximum 4096 program lines (configurable in config.h)
  - Maximum 255 characters per line
  - Maximum 256-level GOSUB/FOR stack depth
  - 64-level expression evaluation stack
  - Single-threaded execution only (no SPAWN/TASK)
  - No preemptive multitasking between programs

  VIRTUAL CONSOLE:
  - Maximum 8 screen pages (0-7)
  - Text mode: maximum 132 columns x 50 rows
  - Graphics mode: 320x200 fixed resolution (config.h)
  - 16 colors maximum (CGA palette)
  - No hardware sprites (software only via PSET)
  - PCOPY between pages is a full buffer copy

  VIRTUAL TERMINAL:
  - Depends on host terminal capabilities
  - Unicode half-block rendering requires UTF-8 terminal
  - Mouse support not yet implemented
  - Sound is platform-dependent (Windows: Beep API;
    Linux/macOS: no-op; FreeDOS: PC speaker)
  - No true serial port emulation (use external modules)

  VDEV LAYER:
  - Maximum 16 device slots (3 built-in + 13 user)
  - Devices registered from C code only (not from BASIC)
  - Maximum 8 simultaneous file channels (#1-#8)
  - Maximum 1024 characters per vdev_printf() call

  MEMORY:
  - 64K virtual memory space (PEEK/POKE)
  - DEF SEG wraps at 64K boundary
  - No bank switching emulation (single 64K view)
  - MEMMAP reinitializes entire 64K (no partial load)

  GENERAL:
  - All virtualization is software-only
  - No cycle-accurate timing emulation
  - No hardware interrupt simulation
  - No DMA or bus contention effects
  - Machine presets are approximations, not exact replicas

=====================================================================
13. VM DEVICE BUS ARCHITECTURE
=====================================================================

The VM treats devices as an extension of its I/O bus.  When
a BASIC program opens a device-backed channel, the VM's
existing PRINT/INPUT handlers automatically route through
the VDev function pointers.

  EXECUTION PATH (file-backed channel):

    PRINT #1, "Hello"  ->  vm_dispatch(OP_PRINT)
                       ->  fileio_print(1, "Hello", line)
                       ->  fprintf(fp, "Hello")

  EXECUTION PATH (device-backed channel):

    PRINT #1, "Hello"  ->  vm_dispatch(OP_PRINT)
                       ->  fileio_print(1, "Hello", line)
                       ->  vdev_puts(channel->vdev, "Hello")
                       ->  device->dev_puts(device, "Hello")

The VM dispatcher does NOT need to know whether a channel is
file-backed or device-backed.  The fileio layer handles the
routing transparently via the FCHAN_DEVICE mode check.

This means every existing BASIC statement that uses channels
(PRINT #, INPUT #, WRITE #, LINE INPUT #) works automatically
with VDev devices.  No VM changes needed.


=====================================================================
14. DEVICE-BACKED CHANNEL DISPATCH
=====================================================================

The VM sees channels as abstract I/O endpoints.  The fileio
layer now has three dispatch paths:

  Channel Mode    Data Path          Via
  ------------    ---------          ---
  FCHAN_INPUT     fgets(fp)          stdio
  FCHAN_OUTPUT    fprintf(fp)        stdio
  FCHAN_APPEND    fprintf(fp)        stdio
  FCHAN_RANDOM    fread/fwrite(fp)   stdio (binary)
  FCHAN_BINARY    fread/fwrite(fp)   stdio (binary)
  FCHAN_DEVICE    vdev_puts/gets(d)  VDev function pointers

For binary operations on device-backed channels:
  GET #n reads via vdev_read(d, buf, len)
  PUT #n writes via vdev_write(d, buf, len)

For IOCTL on device-backed channels:
  IOCTL #n, cmd, arg  ->  vdev_ioctl(d, cmd, arg)

The VM handles this transparently.  BASIC programs never
need to know the implementation details.


=====================================================================
15. EVENT-DRIVEN DEVICE I/O (ON DEVICE GOSUB)
=====================================================================

Future syntax for event-driven I/O:

  ON DEVICE #n GOSUB line_num

This registers a callback.  When the device on channel #n
has data available (dev_poll returns 1), the VM interrupts
the current execution, pushes a GOSUB frame, and transfers
control to the handler line.

  Example — sensor interrupt:

    10 MODULE "SENSOR"
    20 OPEN "TEMP:" FOR INPUT AS #1
    30 ON DEVICE #1 GOSUB 1000
    40 REM Main loop does other work
    50 FOR I = 1 TO 100000
    60   A = SIN(I) * COS(I)
    70 NEXT I
    80 CLOSE #1
    90 END
    1000 REM Sensor interrupt handler
    1010 LINE INPUT #1, T$
    1020 PRINT "Sensor reading: "; T$
    1030 RETURN

  Implementation in the execution loop:

    Before step 1 ("check state == VM_RUNNING"), the VM
    scans all channels with ON DEVICE handlers.  For each:
      1. Call vdev_poll(channel->vdev)
      2. If returns 1, push GOSUB frame with return address
      3. Jump to the registered handler line
      4. On RETURN, resume where we left off

  This provides cooperative multitasking for device events.
  The VM checks for device events between BASIC statements,
  not within them, so execution is never interrupted mid-
  statement.


=====================================================================
16. DEVICE HOT-PLUG IN THE VM
=====================================================================

Devices with VDCAP_HOTPLUG can appear or disappear while
the VM is running.  The VM handles this gracefully:

  DEVICE APPEARS:
    - Module registers VDev via vdev_register()
    - BASIC program discovers it via DEVICES or DEVICEFIND()
    - OPEN connects the channel

  DEVICE DISAPPEARS:
    - dev_status() returns -1
    - dev_poll() returns -1
    - dev_read/dev_write return -1
    - dev_puts/dev_gets return -1
    - ON ERROR GOTO handler fires

  Safe pattern for hot-plug:

    10 ON ERROR GOTO 100
    20 OPEN "USB:" FOR RANDOM AS #1
    30 PRINT #1, "Hello USB Device!"
    40 CLOSE #1
    50 GOTO 200
    100 PRINT "Device not available or disconnected"
    110 RESUME 200
    200 REM Continue program...

  The VM never crashes on device disconnection.  Every VDev
  function pointer NULL-check returns -1, which propagates
  up to an ERR_HOW error that ON ERROR GOTO catches.
