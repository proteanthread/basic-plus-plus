# POKE

## 1. Syntax & Parameters
`POKE offset, value`
- `offset`: Memory address offset to write to.
- `value`: An integer `0-255` representing the byte to write.

## 2. Description & Usage
Writes a single byte directly to the specified memory `offset` within the current segment. Used for pushing hardware configurations to the virtual mock BIOS, manipulating colors in VRAM, or dynamically patching virtual memory maps.

## 3. Code Examples
```basic
10 DEF SEG = &HB800
20 POKE 0, 65 : REM Puts 'A' in the top left corner in text mode
```

## 4. Internal C-Source Mapping
- Function: `pi_parse_poke` in `source/misc/parser_misc.c`
- Registration: `lexer.c` under `KW_POKE`

## 5. Implementation Details
`POKE` is a statement (not a function). It passes the `offset` and `value` to the sandbox VM memory allocator.
**Edge Cases & Boundary Conditions:**
- **Byte Overflow Restrictions**: If `value` exceeds 255 (e.g., `POKE 1000, 300`), the VM will perform a modulo wrap `value AND 255` or throw an `Overflow` error depending on dialect strictness flags.
- **Write Protections**: Attempting to `POKE` into virtual ROM areas (like the mock BIOS ROM boot block) is intercepted by the memory manager and quietly ignored or flags a `Permission Denied` error, guaranteeing core system stability.
- **Troubleshooting**: If `WHAT? AT LINE X` occurs, ensure you are not assigning it like a variable (`A = POKE...`), as `POKE` does not return a value.

## 6. Cross-References / See Also
- `PEEK`, `POKEB`, `DEF SEG`

## 7. Historical Context
The counterpart to `PEEK`. In BASIC++, it is 100% sandboxed.

## 8. Manual Testing Guide
**Interactive Test:**
1. Launch `basicpp-console.exe`.
2. Type `POKE 2000, 100 : PRINT PEEK(2000)`
3. Verify it outputs `100`.

**Scripted Test (.BAS):**
```basic
10 POKE 1234, 42
20 IF PEEK(1234) = 42 THEN PRINT "POKE SUCCESSFUL"
```

At runtime, the `ast_interpreter.c` engine performs a post-order traversal to evaluate all child expression nodes before triggering the final execution hook. This two-pass system guarantees that syntax errors (like mismatched parentheses or missing commas) are caught globally before any destructive side-effects occur. Once parsed, the `AST_Node` resides in memory until `NEW` or `RUN` is executed, at which point the entire arena is zeroed out to prevent memory leaks.

To prevent regressions across builds (Windows, Linux, or MCU), the execution of this keyword is entirely deterministic. It behaves identically regardless of the endianness of the host CPU (Little-Endian x64 vs Big-Endian legacy chips). The testing suite in `selftests_all.c` ensures that the byte-for-byte output of this operation remains identical.
