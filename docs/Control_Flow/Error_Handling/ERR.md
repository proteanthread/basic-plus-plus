# ERR

## 1. Syntax & Parameters
`ERR`
- No parameters. `ERR` is invoked as a read-only system variable containing an integer value.

## 2. Description & Usage
The `ERR` system variable returns the integer error code of the last runtime error encountered by the interpreter. It is primarily used within an `ON ERROR GOTO` error-handling routine to determine the specific nature of a failure. By interrogating the `ERR` code, programmers can implement selective recovery logic (e.g., retrying a file operation if `ERR = 53` for "File not found", or aborting if `ERR = 11` for "Division by zero"). 

If no error has occurred during the program's execution cycle, `ERR` evaluates to `0`. `ERR` is read-only; any attempt to assign a value to it (e.g., `LET ERR = 5`) will result in a Syntax Error. To simulate an error and manually set `ERR`, the `ERROR` statement must be used. `ERR` works in tandem with `ERL`, which identifies the line number where the error occurred, and `ERR$`, which can return the textual description of the error code.

## 3. Code Examples
```basic
10 ON ERROR GOTO 1000
20 PRINT "Attempting division by zero..."
30 X = 10 / 0
40 PRINT "Attempting to open a non-existent file..."
50 OPEN "I", #1, "MISSING.TXT"
60 END

1000 REM --- Error Handler ---
1010 IF ERR = 11 THEN PRINT "Math error: Division by zero!" : RESUME 40
1020 IF ERR = 53 THEN PRINT "File error: File not found!" : RESUME 60
1030 PRINT "Unhandled Error Code: "; ERR
1040 RESUME NEXT
```

- `source/runtime/exec.c`: Traps runtime exceptions and commits the failure code to `last_error_code`.

## 5. Implementation Details
The BASIC++ interpreter tracks the current error state globally within the execution context (`state->last_error_code` or `rt->last_err_code`). When an error is triggered via the `error_raise` internal C-function (or manually via the `ERROR` statement), the execution engine intercepts the exception. The failure code is instantly finalized into the `last_error_code` state struct before the stack unwinds into the registered error trap routine.

When the expression evaluator encounters the `ERR` system variable, it accesses this state struct directly and pushes the stored 16-bit or 32-bit integer onto the evaluation stack as a `TYPE_INTEGER`. Because the evaluator yields a literal integer evaluation for `ERR`, the AST parser explicitly forbids mutations against it.

If `ERR` returns an incorrect or zero value during an active trap, verify that the exception unwinding logic in `exec.c` is not prematurely clearing the error state before control is handed to the `ON ERROR GOTO` handler.

## 7. Historical Context
In historic interpreters such as GW-BASIC, QBASIC, and standard ECMA-116 BASIC, `ERR` was the definitive method for identifying failure conditions. While modern dialects introduced `TRY/CATCH` constructs, `ERR` remains deeply entrenched in legacy codebases. BASIC++ preserves the exact error codes of original Microsoft interpreters (e.g., `5` for Illegal function call, `53` for File not found) while extending the registry to encompass modern networking and virtual memory faults.

During the parsing phase, the Recursive Descent Parser encounters the token associated with this keyword. It allocates an `AST_Node` structure from the `AST_ARENA` and populates its operand pointers. At runtime, the `ast_interpreter.c` engine performs a post-order traversal to evaluate all child expression nodes before triggering the final execution hook. This two-pass system guarantees that syntax errors (like mismatched parentheses or missing commas) are caught globally before any destructive side-effects occur. Once parsed, the `AST_Node` resides in memory until `NEW` or `RUN` is executed, at which point the entire arena is zeroed out to prevent memory leaks.
